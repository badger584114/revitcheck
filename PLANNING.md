A web app that ingests PDF or DWG sets of civil engineering drawings (bridges, retaining walls) and runs two categories of automated review: a **drafting check** (standards, annotation, cross-sheet, spelling/revisions) and a **geometry check** (dimensional consistency, full structure reconstruction from setout data, cross-checking against setout tables). A third input, an uploaded **client specification document**, can auto-generate project-specific rules that feed both engines (§6).

## 1. Recommended stack

**Backend: Python (FastAPI)**

Python has the strongest ecosystem for the two hardest problems here — CAD/PDF parsing and geometric validation:

- `ezdxf` — reads/writes DXF, gives structured access to lines, polylines, arcs, circles, text, dimensions, blocks, layers. **Deferred/conditional** — see the DWG handling note below; don't build this until PDF-only is actually proven insufficient.
- `ifcopenshell` — reads IFC (3D BIM interchange format). **Installed 2026-08-12** (`requirements.txt`) — candidate source of ground-truth 3D geometry for §5b structure-reconstruction on sheets with no setout table (confirmed 2026-08-11 to be most of them — see §5's note). Confirmed a clean prebuilt-wheel install on this environment's old x86_64-under-Rosetta Python (no repeat of the `cryptography` build-from-source issue §10 documents). First ingestion slice built against two real `.ifc` files (`samples/BR06/`, `samples/BR08/`) — see §5's IFC subsection for the real schema-general-vs-project-specific findings this surfaced.
- `PyMuPDF` (fitz) — extracts vector paths, text (with position), and images from PDF
- `pdfplumber` — table extraction (setout tables, revision blocks, title blocks) from PDF
- `python-docx` — text/table extraction from Word-format client specs
- `shapely` / `numpy` — geometric operations, tolerance checks, polygon closure, coordinate math
- `opencv-python` + `pytesseract` (or `paddleocr`) — OCR for scanned/raster sheets
- `pyspellchecker` / LanguageTool (self-hosted) — spelling, base dictionary locale **en-GB** (British spelling — "specialised", "colour", "kerb", not the US variants), layered with a custom engineering/abbreviation dictionary
- Self-hosted LLM (local Llama/Mistral-class model via vLLM or Ollama) — client spec requirement extraction (§6); no cloud LLM API, per the zero-outbound-internet constraint (§9)

**DWG/DXF handling — resolved by evidence, split by engine.** This was originally a hedge against uncertainty ("conditional, build only if PDF proves insufficient"); building Stages 1–3 against the real sample resolved it in both directions at once, not just one:

- **Drafting checks (§4): PDF is confirmed sufficient.** Title block extraction, revision schedule parsing, spelling, and the cross-sheet reference graph's marker detection all work reliably off `PyMuPDF` vector/text extraction — proven against the real 37-page sample with a passing test suite, not just argued for. No DXF needed here.
- **Geometry checks (§5): PDF is confirmed *insufficient* for dimension-line reconstruction specifically.** Building the single-sheet dimensional-consistency check (§9 step 3) hit a real wall: a PDF carries no native `DIMENSION` entity, only raw vector paths, so associating a dimension's text label with the correct line is pure spatial heuristics — line-segment matching, span-merging, arrowhead-pair matching were all tried against the real sample. Each worked on some cases and silently picked the *wrong* line on others, especially where dimensions repeat/stack (e.g. the same pile-spacing value dimensioned ~10 times down a row) — proximity alone can't disambiguate which of several nearby candidates belongs to which label. A DXF `DIMENSION` entity carries the measured value and witness-line references directly, which removes this ambiguity at the source rather than trying to out-heuristic it.

**The resulting split: drafting checks run on PDF; geometry checks require DXF/DWG.** This is workable specifically because geometry checks are run far less often than drafting checks in practice — most check runs only need drafting, and §2's `CheckRun` scope selection already models "drafting-only" vs "drafting + geometry" as separate choices. That scope selection now has a concrete precondition: **"drafting + geometry" requires a DXF source** (native DXF upload, or DWG converted via ODA File Converter + `ezdxf`); a PDF-only project can only run drafting-only checks, and the UI should say so rather than silently attempting (and unreliably guessing at) geometry checks from a PDF. See §2 and §5 for how this plays out in the pipeline and tolerance/mechanics sections respectively.

DXF parsing (`ezdxf`) is therefore committed work for Stage 3+, not indefinitely deferred — scoped specifically to what geometry checks need (DIMENSION entities, block/insert attributes for setout data, layer table), not a general DXF-parity reimplementation of everything the PDF pipeline already does well.

**Frontend: React + TypeScript (Next.js)**

- PDF.js for PDF rendering, a custom DXF→SVG/Canvas renderer (or convert DXF to PDF server-side via ODA/`ezdxf`+`matplotlib` for a unified viewer)
- Canvas/SVG overlay layer to highlight flagged issues directly on the drawing, with click-to-jump between issue list and drawing location

**Data & infra**

- PostgreSQL — auth accounts and firm-level config only (firm-wide glossary, named standard rule bundles, §4). **Scope narrowed 2026-08-10** — see "Stateless by design" below: client drawing data, extracted IR, and generated Issues are never persisted, so the original PostGIS/geometry-storage rationale for this row no longer applies. Still the right general-purpose choice given accounts + relational firm config need to live somewhere, just a much smaller footprint than originally planned.
- Redis + Celery (or RQ) — async job queue for a single session's processing (parsing, OCR, and geometry reconstruction are CPU-heavy and too slow for a request/response cycle); job state itself is transient by nature, which fits the ephemeral model without change
- S3-compatible object storage — **scratch space for one session's processing, not drawing storage.** Uploaded files, converted DXF/DWG, and rendered overlays exist only for the lifetime of a check run; see "Stateless by design" below for the purge policy
- Docker Compose for local dev; containers for API, worker, DB, Redis, MinIO (local S3)

This stack is a recommendation, not a constraint — flag if there's an existing internal stack (e.g. .NET shop, Azure-only infra) this needs to fit into instead.

## 2. Processing pipeline

```
Upload (PDF/DWG) 
  -> File type detection & DWG->DXF conversion (ODA)
  -> Extraction (per sheet):
       - Vector entities (lines, polylines, arcs, circles, dimensions, blocks, layers)
       - Text entities (native) + OCR text (for raster content)
       - Tables (setout/coordinate tables, revision blocks, title blocks)
  -> Normalization into common Intermediate Representation (IR)
  -> Drafting Check Engine   \
  -> Geometry Check Engine    > run against IR, produce Issues
  -> Report generation (in-app + exportable PDF/Excel)
```

Each stage runs as an async worker job; job status is polled/streamed to the frontend. A client spec upload (§6) runs a parallel extraction pipeline that feeds rules into the two check engines before they run against the IR.

**Stateless by design — no persistent project/session data. Decided 2026-08-10.** This app is not a project-management tool with saved history: a user logs in, picks a workflow (drafting-only or drafting + geometry), uploads a drawing set (+ optional client spec), runs checks, downloads the report/markup set, and the server clears everything from that session — uploaded files, extracted IR, generated Issues, rendered markups. The next login starts completely fresh, with no list of past projects or runs to return to. This is a client-confidentiality decision as much as an architectural one — see §10 — drawing sets never linger on the server past report delivery.

What this does and doesn't change:
- **Only firm-level config persists** (§4's layer 2: the firm-wide glossary, named standard rule bundles). That's operational config the app needs to function consistently across sessions, not client drawing data, so it's exempt from the clear.
- **§4's "project-level config" layer effectively collapses.** That layer was originally a project admin's persistently-edited overrides (site reference values, glossary additions, tolerance tweaks) layered on a firm standard. With no persistent project to attach it to, a session instead starts from a firm-level standard bundle and optionally layers a small rules file uploaded alongside the drawings for that session — see §4 for how this reshapes the schema's layer 3.
- **§7's cross-run revision diffing is dropped**, not adapted — see §7 for why and what replaces it.
- **§6's spec-derived-rule review/correction happens within the same session**, before the final report, not as a separately revisitable admin screen — see §6.
- **Auth still exists** (a login gates who can use the tool) but carries no per-user saved state — it's access control, not a user profile with history.

**Check scope selection.** Extraction/IR-normalization always runs (both engines depend on it), but the two check engines execute independently against the IR, so a `CheckRun` records which scope was requested:

- **Drafting only** — runs §4 against the IR, skips §5 entirely. Fast, no reconstruction cost; useful for early-stage/incomplete sheet sets where geometry reconstruction isn't meaningful yet (e.g. setout data not finalized), or when an engineer just wants a quick drafting-convention pass. Works from PDF alone.
- **Drafting + geometry** — runs both engines. **Requires a DXF source for the geometry half** (native DXF upload, or DWG converted via ODA) — §1's DWG/DXF section explains why: PDF-only dimension-line reconstruction proved unreliable in practice (repeated/stacked dimensions defeat spatial-proximity matching), where DXF's native `DIMENSION` entity carries the measured value and witness-line references directly. If a project has only submitted PDF, this option isn't available — the UI should say so explicitly ("upload DXF/DWG to enable geometry checks") rather than attempt it and silently produce unreliable flags.

There's no "geometry only" mode — geometry checks (§5) still consume drafting-extracted entities/text (title block scale, units) as reconstruction inputs, so drafting extraction is a prerequisite even when its *rule* output isn't wanted; scope selection only controls which engines' Issues get generated and reported, not which extraction steps run. The scope choice is made explicitly at the start of every session (no "last run" to default from, per "Stateless by design" above) — the frontend expression of this is two upload dropzones, PDF always shown/required and a CAD (DXF/DWG) dropzone that only appears once "drafting + geometry" is selected, matching the precondition above. Client-spec-derived rules (§6) respect the same scope split: narrative/presence rules only fire in a drafting-inclusive run, numeric/threshold overrides only apply when geometry runs.

**Upload handling for large files.** Full drawing packs are routinely 100MB+ as a single PDF (many sheets in one file), so there's no hard cap dictated by the architecture, but every layer the upload passes through defaults to limits far below that and needs explicit, coordinated configuration rather than discovering a silent 413 in production:

- **Don't proxy the raw file through the API app process.** Have the browser upload directly to object storage (MinIO/S3-compatible) via a presigned multipart upload URL issued by the API, then have the browser notify the API once the upload completes so a processing job can be queued. This keeps a 100MB+ transfer off the API server's request memory/threads entirely, decoupling upload reliability from API server config — the API is only ever handling small JSON requests, never streaming the file itself.
- **Reverse proxy / ASGI limits** (nginx `client_max_body_size`, any load balancer body-size cap, Uvicorn's own limits) still need raising if anything sits in front of the presigned-upload path (e.g. the presign-request endpoint itself, or a dev setup without direct-to-storage upload yet) — these default low (often 1MB) and silently reject otherwise-fine uploads.
- **Chunked/resumable upload** on the frontend (e.g. multipart PUT in parts, or a resumable protocol) rather than a single request — on a 100MB+ file over an office network, a single-shot upload that fails at 95% and restarts from zero is a real usability problem, not a hypothetical one.
- **Size limit is a configurable ceiling, not hardcoded** — same "config, never a hardcoded constant" principle as tolerances elsewhere in this doc. Start generous (e.g. default 500MB/file) and adjust per deployment once real pack sizes are known, rather than picking a number that turns out to clip a real project.
- **Processing time is already decoupled from upload** — extraction/OCR/geometry reconstruction run as async worker jobs (per the pipeline above), so a large pack taking minutes to process doesn't block anything; the actual resource risk for large packs is OCR over many raster/scanned sheets (CPU/memory-heavy), not file size or vector/text extraction (`PyMuPDF` opens and reads pages lazily, not the whole file into memory at once) — worth sizing OCR worker resource limits independently from upload size limits.
- **Purge policy (per "Stateless by design" above).** Everything staged in object storage for a session — uploads, converted DXF, rendered markups — needs a defined deletion trigger, not indefinite retention. Exact policy is an open question (§11): the safest default is delete-on-report-download-confirmed, with a timeout-based fallback (e.g. purge after N hours of session inactivity regardless, in case the browser tab is closed before download completes) so an abandoned session can't linger indefinitely either.

**Processing at scale (200–250 sheet packs on large structures).** At that page count, a single serial job over the whole PDF is the wrong shape — fan out per-sheet extraction as independent parallel worker tasks (a Celery group/chord) instead of one big job for the whole file:

- **Parallel extraction, per sheet.** Each sheet's vector/text/table extraction is independent of every other sheet, so it parallelizes cleanly across the worker pool — wall-clock time for a 250-sheet pack scales with worker concurrency, not sheet count processed serially.
- **Granular progress, not a spinner.** Job status should report sheet-level progress (e.g. "142/250 sheets extracted"), not just started/done — a multi-minute job on a large pack needs visible progress, and per-sheet granularity falls out naturally once extraction is fanned out per sheet.
- **Failure isolation per sheet.** One corrupt or unusual sheet (bad embedded image, malformed vector data) shouldn't abort the other 249 — report per-sheet extraction status (`ok` / `failed: <reason>`) the same way §5b already reports per-point reconstruction status, and run the check engines against whatever extracted successfully rather than failing the whole run over one bad sheet.
- **Rule scheduling splits by scope.** Most drafting rules (§4) and single-sheet geometry checks (§5a) only need their own sheet's IR, so they can run the moment that sheet's extraction completes — no need to wait on the other 249. Cross-sheet rules (§4's cross-sheet consistency, §5's cross-view matching, §5b's multi-sheet reconstruction) genuinely need the full extraction fan-in — a join after every sheet's extraction task completes — since they depend on entities/tables from sheets other than their own. Worth tagging each rule in the catalog with a `scope: single_sheet | cross_sheet` attribute so the scheduler knows which tier to run it in.
- **Incremental review as a UX consequence, not just a backend optimization.** Since single-sheet results can be ready well before all 250 sheets finish, the issue list can populate sheet-by-sheet rather than the engineer staring at a blank screen until the entire pack completes — worth designing the frontend's job-status/issue-list UI to stream results in rather than reveal them all at once, given pack sizes at this scale.

## 3. Intermediate Representation (IR)

A common schema both engines operate on, regardless of whether the source was PDF or DXF:

- **Project** → **Sheet** (one per drawing page/tab)
- **Sheet** metadata: title block fields (drawing number, title, scale, revision, date, discipline), units, coordinate origin
- **Entities**: lines, polylines, arcs, circles, text (with position/rotation/style), dimensions (with measured value + witness lines), blocks/inserts (symbols, north arrows, detail bubbles, section markers), hatches
- **Tables**: parsed rows/columns for setout tables (point ID, northing/easting/elevation or station/offset/level), revision tables, schedules
  - **`Sheet.tables_scanned` (added 2026-08-17)** records whether ruled-table extraction actually *ran* for that sheet. `pdfplumber`'s `find_tables()` was profiled at 91.5% of all PDF ingestion (97.8s of 106.9s on the real 37-sheet sample), returning 733 tables of which exactly one was a real schedule — a civil drawing's reinforcement detailing and hatching manufacture grids that aren't tables, and the detector's cost is sharply superlinear in edge count (one real sheet: 195,367 edges, 22.8s alone). `extraction/tables.py`'s `page_may_hold_setout_table` now gates it on a cheap text test for **Easting and Northing** — confirmed by the user (2026-08-17) as the one real invariant of a setout table, unlike its ID column, whose name varies by project. Ingestion went 106.8s -> 11.1s with the real 28-point schedule unchanged. Two other approaches were measured and rejected first: tuning `edge_min_length` was *slower* (82s -> 97-102s), and cropping out the title block/border was slower still (88.4s -> 94.1s) *and* changed real extraction results. **The trade-off is real and deliberate:** `Sheet.tables` no longer means "every ruled table on this sheet" but "tables on sheets that could carry setout data" — a bar-bending schedule or materials list now yields nothing. `tables_scanned=False` marks those sheets so "nobody looked" stays distinguishable from "there was nothing there", and `ingest_pdf(table_scan_keywords=...)` widens or disables the gate.
- **Layers**: name, color, linetype, per project layer-naming convention
- **References**: cross-sheet edges connecting a source marker entity (section cut, detail bubble, match line, or a general-note text match) to a target view/sheet, each with a `type` (section/detail/match_line/general_note), a resolution state (`resolved`/`unresolved`), and a confidence score. Built as its own pass across the whole sheet set (needs every sheet's entities/text extracted first — see §2 "Processing at scale"), consumed by both engines: drafting's cross-sheet consistency rule (§4) and geometry's cross-view dimensional matching (§5a). See §4 for the full extraction/resolution mechanics.
- **`IfcElement`/`IfcModel`** (built 2026-08-12, `ir.py`) — §5's proposed third geometry source, an IFC 3D-model export's elements (schema-general: IFC4 entity class + `PredefinedType` + `GlobalId` + world-space bounding-box geometry, deliberately not this firm's Revit `Name`/property-set conventions — see `extraction/ifc_source.py`'s docstring). Project-level, not per-sheet — attached via `Project.ifc_model`, not folded into `Sheet`/`DxfSheet` the way those two are, since one IFC export covers the whole model rather than joining 1:1 to a sheet. Consumed by `checks/geometry.py`'s `geometry.ifc_setout_consistency`.

Extraction from PDF vs DXF converges on this same schema so both check engines are format-agnostic.

## 4. Drafting check engine

Rule-based, with rules grouped by category and configurable per project/standard (a project can select "AASHTO-style", "internal firm standard", state DOT standard, etc., plus add custom rules).

| Category | Examples |
|---|---|
| Standards/conventions | Layer naming matches convention, linetypes/weights correct, text style/font consistent, scale stated matches actual, north arrow present, title block fields complete |
| Annotation/dimension completeness | Every drawn feature requiring a dimension has one, section cut markers have a corresponding section sheet, detail bubbles have a corresponding detail sheet, all callouts resolve to something that exists |
| Cross-sheet consistency | Build a reference graph (sheet A section marker → sheet B section view); verify every reference resolves and labels match; detail/section titles match their callouts |
| Spelling | Run extracted text through a spellchecker against an **en-GB (British English)** base dictionary — not en-US — so correct British spellings (`specialised`, `colour`, `kerb`, `programme`, ...) never flag, plus a custom glossary (engineering abbreviations, material names, project-specific terms) to suppress domain false positives |
| Revisions | Revision clouds/triangles on a sheet must have a matching row in that sheet's revision table; revision numbering must be sequential and consistent across the sheet set — see mechanics below |
| Project-specific | Rules engine accepts a per-project rule set (JSON/YAML: regex text checks, required-element presence/absence, custom tolerance overrides) defined by the project admin — no code change needed to add a project-specific check. Client-spec-derived rules (§6) populate this same rule set automatically. |

**Rule engine design:** each rule is a small function `(IR, config) -> [Issue]`. Rules are registered in a catalog; a project's active rule set is just a list of rule IDs + parameters. This makes "ask for project-specific things to be checked" a config-time operation, not a dev-time one.

**Project-specific rule primitives.** The "Project-specific" row above already covers three: regex text checks, required-element presence/absence, and tolerance overrides on existing checks — but those are all *internal*-consistency primitives (does a field exist, match a pattern, agree with another drawn value). A field-value-correctness check — e.g. a client-mandated lat/long parameter in the title block, which needs to be verified as actually correct, not just present — needs a fourth primitive plus one extraction fix:

- **Extraction gap first.** §3's title-block field list (drawing number, title, scale, revision, date, discipline) is fixed; a project-specific field like lat/long isn't in it, so nothing can check it until extraction knows to pull it out. The title-block field list needs to be project-extensible — a config entry naming the field (by label text or a fixed title-block position/region to read from) so an arbitrary firm/client-specific field becomes part of that sheet's IR metadata before any rule runs against it.
- **Fourth primitive: value-correctness against a reference.** Compares an extracted field to an **expected value**, which can be either a literal configured once at project setup (simplest — an admin enters the project's correct site lat/long once, every sheet's title-block value is checked against it) or a value derived from other project data (e.g. the project's site origin/coordinate system definition transformed to lat/long) — start with the literal-value form for MVP, same "structured/simple case first" sequencing used everywhere else in this doc, and treat the computed/derived form as a later enhancement.
- **Tolerance as real-world distance, not a naive value delta.** For lat/long specifically, `abs(stated − expected)` in degrees is misleading — a degree of longitude covers a very different real distance depending on latitude. Compute an actual geodetic distance (haversine or similar, e.g. via `pyproj`/`geopy`) between stated and expected coordinates and compare that against a distance tolerance (e.g. "within 10m"), not a raw coordinate delta. This is the general lesson, not lat/long-specific: any project-specific numeric correctness check should use a tolerance in the value's own real-world unit, never assume a flat delta on the raw stored representation is meaningful.
- **Sheet-to-sheet consistency is a separate, cheaper check worth having too.** Independent of "is it correct," every sheet in the set should show the *same* lat/long — a same-extracted-field-across-sheets equality check, reusing the same extraction but no reference value or geodetic math needed. Worth registering as its own lightweight rule rather than folding into the correctness check, since it can catch a class of error (one sheet's field silently diverging from the rest) even before anyone's confirmed what the "correct" value is.

**Custom dictionary / glossary management.** A term flagged as misspelled must be dismissible permanently, not just per-run, otherwise recurring engineering terms (`abutment`, `chainage`, product/material trade names, client/project codenames) create standing noise that trains engineers to ignore the spelling check entirely. Two tiers, both stored as data (not code) and both feeding the same en-GB-based spellchecker:
- **Firm-wide glossary** — terms approved once, apply to every project (engineering abbreviations, standard material/product names, common trade terms).
- **Project glossary** — terms scoped to one project (site names, client-specific codenames, one-off product names) — doesn't pollute the firm-wide list with names that won't recur.

Adding a term is one click from the issue list ("Add to dictionary" on a spelling Issue — choose firm-wide or project scope), so the flagged-word list itself doubles as the intake path rather than requiring a separate admin screen. Re-running a check after an addition must not re-flag that term. This is the same "config change, not code change" principle as the rest of §4's rule catalog, applied to the spelling dictionary specifically.

**Cross-sheet reference graph — mechanics.** Referenced by name in the Cross-sheet consistency row above and reused by the geometry engine's cross-view matching (§5a), but it's shared infrastructure worth specifying once rather than each caller re-deriving it. It's built as its own pass, not folded into either engine.

*Reference types* (a project-configurable list, since drafting conventions vary by firm/discipline):
- **Section marker → section view** (a cut-line symbol on a plan/elevation tagged e.g. `A`, pointing to a view titled `SECTION A-A` on some sheet)
- **Detail bubble → detail view** (a circled tag e.g. `4/S-201`, pointing to a view titled `DETAIL 4` on sheet `S-201`)
- **Match line → adjoining sheet** (a line across a large plan tagged `MATCH LINE — SEE SHEET S-103`, connecting two sheets at a specific edge rather than pointing at a titled view)
- **General note reference** (free text, e.g. "see Detail 4 on Dwg S-201", inside notes/specs text rather than a graphic symbol)

*Extraction — built and calibrated against `samples/T2DPAA-T2D-C3S-BR-DRG-101000.pdf` (`extraction/references.py`); this section originally anticipated a shape-detection approach and real-sample evidence changed it in two ways worth recording, same as §1's DWG/DXF section:*

1. **Text adjacency, not vector shape, turned out to be the reliable signal.** The plan here was to detect a circle/hexagon/pentagon symbol first, then proximity-match its text. On the real sample, SECTION markers are a circular vector path but DETAIL markers aren't (confirmed: no matching vector path near a DETAIL marker's text) — so shape-first detection would silently miss a whole marker family. What both share regardless of symbol: a short tag (a digit or single letter — `"3"`, `"A"`) stacked directly above or below a drawing/sheet number (e.g. `"2871023"`), a few points apart. Detection keys off that text pattern alone — simpler, and confirmed more robust than nailing every symbol variant's geometry. (Limitation: only single-digit/single-letter tags are handled yet; richer formats like `"A1"` or letter-prefixed sheet numbers aren't, until a sample surfaces one.)
2. **A marker's printed sheet number names "where the counterpart is", not "where this marker sits."** The identical `(tag, sheet number)` text appears at *both* ends of a reference: once at the callout (e.g. a section cut line in a plan view), pointing forward to the sheet the section is actually drawn on; once beside the section/detail view's own title, pointing back to the sheet the callout was made from. This means the target index (below) is built from view *titles*, not from markers directly — a marker sitting right next to a matching title on its own sheet is the view's own self-identifying marker (already indexed, nothing to resolve); every other marker is a callout to resolve against that index.

*General note references* (free text, e.g. "REFER TO SHEET No. 2871005 TO 2871008") — **built 2026-08-14**, `_extract_note_references` in `extraction/references.py`. Confirmed real convention: a `"<REFER|SEE> [TO] SHEET [No.] <digits>[ TO <digits>]"` sentence, calibrated against both `samples/BR06/` and `samples/BR08/`. Two real findings shaped the scope, both documented in the module's docstring: (1) a verb ("REFER"/"SEE") is the one signal that tells a real note apart from an unrelated field sharing the same "SHEET <digits>" shape (a real false positive found: BR06's title-block-adjacent "INDEX SHEET REFERENCE: 8011 SHEET 2871002" legend), and (2) a note explicitly naming another drawing set ("REFER TO DRAWING 8003, SHEET No. 2374001" — a real, common convention for citing a different discipline's own package) is deliberately excluded rather than extracted as an always-unresolved `Reference`, since one ingested `Project` is one drawing set and that sheet number is expected not to resolve here. `_extract_view_titles` still separately guards against misreading a note sentence as a view title (a body-text word like "REFER"/"SEE" immediately before "SECTION"/"DETAIL" excludes the match) — a different mechanism from the note-reference extraction above, both documented in the module's docstring.

*Resolution algorithm (as built):*
1. **Build a target index first, across the whole sheet set** — scan every sheet for a `SECTION <tag>`/`DETAIL <tag>` view title and index by `(tag, sheet_number)` where `sheet_number` is the sheet the title itself was found on. This pass only makes sense after the cross-sheet extraction fan-in (§2 "Processing at scale") — it's a `cross_sheet`-scope operation by definition, same tier as the cross-sheet rules that consume it.
2. **For each marker that isn't itself a view's own self-identifying marker** (see point 2 above), parse its tag/sheet-number text and look up an exact match in the target index.
3. **Exact match** → resolved edge, confidence 1.0.
4. **No exact match** → unresolved, but not treated as one uniform failure: confidence 0.0 if the named sheet doesn't exist anywhere in the set (an unambiguous dead reference), confidence 0.3 if the sheet exists but doesn't carry a matching title (could be a genuine gap or this heuristic's own extraction miss) — never silently upgraded to resolved either way, same "confidence, not silent" principle used for geometry reconstruction (§5b) and spec extraction (§6). True fuzzy/edit-distance matching was considered and skipped for now — tags this short (1-2 characters) don't carry enough signal for edit distance to mean much; worth revisiting once general-note references (longer strings) are built.
5. **Unresolved → Issue**, located at the source marker, using the markup label already defined in §8: `No match: <ref>` (e.g. `No match: Detail 4/2871024`).

*Reuse by the geometry engine (§5a):* cross-view dimensional comparison only runs between two views connected by a **resolved** edge in this graph (skip low-confidence or unresolved pairs rather than guess-matching by proximity/value alone, per §5a's existing "skip rather than guess" rule) — this graph is the actual mechanism behind that reuse, not just a conceptual link.

*Scoping.* Symbol-based resolution (section markers, detail bubbles — deterministic, geometric, highest value) was built first, same sequencing §6 uses for narrative spec extraction (structured/numeric case proven before the open-ended text-parsing one). General-note references followed once that was working against real sheets (see above) — narrowly scoped to the one confirmed real sentence pattern, not a general "extract any sentence that looks like a cross-reference" parser, same "calibrated, not guessed" principle as the rest of this module. Match lines ("MATCH LINE — SEE SHEET S-103") are still not built — no real sample has surfaced one yet.

**Revision consistency — mechanics.** Three distinct pieces of information on a typical sheet have to agree, not just the single cloud↔table link the table above implies:

- **Revision schedule** (bottom-left convention) — the full history table: one row per revision (rev ID, date, description, by/initials). Already covered by the IR's `Table` construct (§3); column mapping is project-configurable since firms vary in column order/naming, same pattern as the layer-/block-naming conventions used elsewhere in §4.
- **Current-revision parameter** (bottom-right convention) — a single title-block field showing the sheet's current revision, already part of Sheet metadata in §3 ("title block fields... revision..."). Neither of these needs an IR change — this rule builds directly on existing IR constructs, unlike the cross-sheet reference graph above which needed a new one.
- **Revision clouds/triangles** — drawn on the sheet body: a closed scalloped-curve entity (the cloud) paired with a small triangle/delta symbol carrying the revision tag. **Built 2026-08-10** (`extraction/revision_clouds.py`), once `samples/T2DPAA-T2D-C3S-BR-DRG-101000_1.pdf` (a second, later-revision export of the same set) gave real AMEND No. 1 sheets with actual drawn clouds to calibrate against — the original sample's every sheet has a single clean revision, `AMEND No. 0`, nothing to detect. Confirms and corrects the assumption this paragraph originally made: cloud/triangle detection does NOT mirror the cross-sheet marker detection above (text-adjacency between a tag and a sheet number) — it's genuinely shape-based, as originally guessed, but the actual shape signal on the real sample turned out finer-grained than "one scalloped-curve entity": PyMuPDF reports each individual scallop bump of a cloud as its own small stroked-curve drawing object (28-96 of them per cloud on the sample), not one closed path with many curve segments, and the triangle tag is a separate 3-straight-line cluster in the same stroke color. Detection clusters same-color curved-stroke path objects by bbox proximity (a minimum object count, not item count, is what filters out the one confirmed false positive: a single red vector-text-glyph object elsewhere on the page with many internal curve items but from one object, not many small ones), pairs the nearest matching 3-line same-color triangle cluster, and reads the tag digit/letter from text overlapping the triangle's bbox — see that module's docstring for the full account, including how it tells a real triangle apart from the unrelated 4-line red rectangle highlight boxes also found on the same sheets. Block/attribute lookup remains the plan if DXF support is ever added (§1).

**Three-way cross-check:**
1. **Schedule ↔ current-rev parameter.** The schedule's latest (highest/most recent) row must match the current-revision title-block field. A mismatch — schedule updated but the title-block parameter forgotten, or vice versa — is one of the more common real drafting errors, and is exactly the kind of thing this check exists to catch. Report both values: `Rev: title block shows C, schedule latest is D`.
2. **Cloud/triangle → schedule row.** Every cloud's revision tag must resolve to a matching schedule row — same resolution algorithm as the cross-sheet reference graph above (normalize, exact match, fuzzy fallback only as a lower-confidence candidate, never silent). Unresolved → the `Rev: cloud has no table row` Issue already defined in §8's markup table.
3. **Sequential numbering.** Schedule rows themselves must be sequential and non-duplicated — no skipped or repeated rev IDs.
4. **Schedule row with no matching cloud — informational, not a hard fail.** Not every revision necessarily has a localized cloud (a general reissue or sheet renumbering can bump the revision without marking a specific area), so flag this at lower severity, and make whether it's enforced at all a project-configurable option — firms differ on how strictly they expect every row to have a corresponding cloud.
5. **Cross-sheet consistency, precisely defined.** Not "every sheet must be at the same revision" — sheets don't all change on every issue, so that would be a false-positive machine. The actual check: sheets whose schedules carry a row with the same *date* should carry the same *revision ID* for that date, so a shared transmittal/issue is internally consistent across the set, without demanding sheets that weren't touched bump their revision anyway.

*Four layers, broadest to narrowest — only the middle two are part of this schema:*

This is the deepest part of the system. Two sub-goals:

**a) Dimensional/geometric consistency**
- Verify drawn geometry matches its own stated dimensions (a rectangle's drawn edge length matches its dimension string)
- Verify a feature's geometry is consistent across plan, elevation, and section views of the same sheet set
- Verify shapes close properly (no gaps in a wall outline, footing polygon, deck edge)
- Configurable tolerance per check (drafting tolerance vs. survey tolerance); client-spec-derived numeric limits (§6) supply the expected value for some of these checks instead of internal cross-referencing

**Mechanics of (a) — this reads from DXF, not PDF (§1's DWG/DXF section): a real Stage 3 build attempt against the PDF sample confirmed dimension-line reconstruction from raw vector paths is unreliable, specifically on repeated/stacked dimensions (spatial-proximity heuristics — nearest line segment, span-merging, arrowhead-pair matching — each got some cases right and silently picked the wrong candidate on others). DXF's native `DIMENSION` entity removes the ambiguity at the source instead of trying to out-heuristic it:**

**Confirmed 2026-08-10 against real converted DXF** (`samples/dwg/`'s 31 files, converted via ODA File Converter and inspected with `ezdxf` — the same "check real geometry before writing code" pass done for every other extraction module in this repo): this section's core premise holds. 470 `DIMENSION` entities across 26 of the 31 sheets (the other 5 are construction-staging diagrams with nothing to dimension, e.g. sheet 101032's "CONSTRUCTION SEQUENCE" — consistent, not a gap). Each carries `measurement` (the raw geometric distance, in the sheet's real-world units — `$INSUNITS`=6, meters, confirmed) and `defpoint`/`defpoint2`/`defpoint3` (dimension-line location + both witness-line origins) directly, exactly as this section assumed, no proximity inference needed. **Also confirmed, not just assumed:** manual text overrides are genuinely common, not an edge case — 252 of 470 dimensions (54%) carry an explicit override — which validates the rounding-grid tolerance design below rather than it being speculative over-engineering. One extra finding worth having for §8's sheet-correspondence work: each `DIMENSION`'s anonymous geometry block is named after the *PDF* sheet, e.g. `DIMBLOCK6-DRG-2871051 - FOUNDATION LAYOUT` on the DXF converted from `...-101051_0.dwg` — independent confirmation, straight from embedded DXF data rather than just filename matching, of the numeric-suffix sheet correspondence §8 already established.

- **Dimension-to-geometry association:** every `DIMENSION` entity already carries its measured value and witness-line/definition-point references directly (`ezdxf` exposes these), so association doesn't need geometric inference at all — no snapping, no proximity heuristics, no risk of picking the wrong nearby line. This is the concrete reason geometry checks require DXF (§1, §2) while drafting checks stay on PDF.
- **Drawn-vs-stated comparison:** take the distance between the DIMENSION entity's own definition points, convert to real-world units using the sheet's stated scale/units from the IR's title block metadata, and compare against the DIMENSION's own measured-value field (already numeric, already unambiguous — no text parsing of `3200`/`3.2m`/`10'-6"` variants needed, unlike the PDF-label-parsing approach originally sketched here). Mismatch beyond drafting tolerance → Issue. **Built 2026-08-10** (`checks/geometry.py`'s `geometry.dimension_consistency`) — one correction and one addition from real data: no title-block/scale cross-reference is actually needed, since a `DIMENSION`'s `measurement` is already a real-world-unit model-space value ($INSUNITS resolves the unit directly, e.g. meters) — DXF's model space removes the paper-scale ambiguity a PDF page-space measurement would have had, not just the dimension-association ambiguity this section already called out. And: not every `DIMENSION`'s override text is a numeric rounding value to compare — real sheet 101151 (49 dimensions, all overridden) showed letter-tag overrides ("A", "B"...) keying into a separate bar-mark/schedule table, which the check skips rather than misreads as a mismatch (same "skip rather than guess" principle as §4's reference graph).
- **Cross-view matching:** reuse the cross-sheet reference graph already built for callout resolution (§4) to match the same physical feature across plan/elevation/section by label first; only fall back to proximity/value-based matching when there's no explicit callout, and skip the comparison (rather than guess) when match confidence is low — a wrong match is worse than no check.
- **Closure checks:** for anything that should be a closed polygon (footing outline, wall cross-section), sum edge vectors around the loop; a non-zero closing residual beyond tolerance is the Issue, reported with the residual vector so the engineer sees which edge is likely wrong, not just "doesn't close."

**b) Structure reconstruction from setout data + cross-check**
- Extract setout/coordinate data: point tables (northing/easting/elevation, or station/offset/level), alignment/chainage geometry, dimension chains
- Reconstruct the structure's geometry (bridge deck/piers/abutments, retaining wall stem/footing) as a 2D (and where elevation data allows, 3D) model, by walking dimension chains and combining with any explicit coordinate points
- Independently compute coordinates for key points from the *drawn* geometry (e.g., wall corner derived by walking a dimension chain from a known origin) and compare against the *stated* coordinates in the setout table
- Flag discrepancies beyond tolerance, with the specific point/dimension and both values (drawn vs. tabulated) so an engineer can see exactly what disagrees
- Where full reconstruction isn't achievable (missing reference point, ambiguous dimension chain), report partial reconstruction with a confidence/coverage indicator rather than failing silently

**Mechanics of (b) — this is a survey-traverse problem, not a CAD-geometry problem, and the key design call is: don't behave like a survey least-squares adjustment that smooths disagreement away. Surfacing disagreement between independent paths *is* the point of this check, so no averaging/best-fit reconciliation.**
1. **Build a graph.** Setout table rows become nodes (named points with stated N/E/Z or station/offset/level). Dimension entities become edges, each needing a length + direction — sourced from an explicit bearing/distance callout (`N45°30'E 12.450`) where present, otherwise inferred from the drawn vector's own orientation once entity geometry is available.
2. **Pick reference point(s).** Typically a stated coordinate origin, a benchmark, or the first setout row carrying an absolute coordinate.
3. **Traverse the graph** (shortest-path / all-paths, e.g. via `networkx`) from each reference to every other setout point, accumulating dx/dy (and dz where levels exist) along the dimension chain — this produces an independently *drawn-derived* coordinate per point, separate from whatever the table states.
4. **Cross-check against the table.** `delta = derived_coordinate − tabulated_coordinate` per point; flag beyond the configured survey tolerance, always reporting both values plus the delta, never just pass/fail.
5. **Redundant paths are a QC signal, not something to reconcile.** If a point is reachable by two different dimension chains and they disagree, that disagreement is itself flagged as an issue (ambiguous/conflicting dimensioning) — the engine never quietly averages multiple chains into one "best" value the way a real survey adjustment would. **Confirmed 2026-08-15, directly by the user: this case doesn't arise in this domain — bridges are always set out in a linear fashion so the construction team gets simple instructions, so dimension chains here are never genuinely redundant/forking. This was a design hedge, not a real scenario to build reconciliation logic for.** Not implemented, and not planned; see the "Structure reconstruction" status paragraph below.
6. **Partial reconstruction is an expected outcome, not a failure state.** Report each point's status (`reconstructed` / `unreachable` / `conflicting`) plus an overall coverage percentage for the sheet, rather than failing the whole run when one point can't be resolved.
7. **Provenance on every derived value.** Store the exact chain used to reach each reconstructed point (e.g. `origin BM100 → dim '12.450' brg 090° → dim '3.200' brg 000°`) so an engineer can verify the path rather than trust an opaque number — this is the specific form CLAUDE.md's "report *how* you reached a value" requirement takes here.

**Tolerance configuration — drafting vs. survey are different *kinds* of tolerance, not just different numbers.** Source drawings for this project are Revit-authored (DWG/PDF export). Revit models routinely need dimension text manually overridden to round the true modeled length to a buildable value — especially on angled/skewed elements, where the raw geometric length rarely lands on a clean number. That's expected, correct drafting behavior, not noise, and it shapes both tolerances differently.

The rounding grid itself **isn't a single project-level constant** — it's tiered by element type, tighter for setout-critical dimensions (feed directly into structural positioning/the setout table) than for general-arrangement ones. So config is a lookup by category with a fallback default, not one number:
```
rounding_grid:
  default: 5mm
  setout_critical: 1mm   # placeholder — confirm the real figure against samples/
```
Classification into `setout_critical` should be two-source, not purely a manual tag: (1) a project config mapping by layer/dimension-style/element-category, for the general case, and (2) automatic promotion to `setout_critical` for any dimension that's actually an edge in the §5b reconstruction graph (i.e., it directly derives a setout table point) — regardless of whether it was tagged, because getting that specific number wrong has downstream reconstruction consequences even if a drafter wouldn't otherwise think of it as "setout-critical." Reusing the graph classification here means the two engines don't need separately-maintained lists of which dimensions matter most.

- **Drafting tolerance (§5a, drawn vs. stated dimension):** a flat numeric delta handles routine rounding badly — loose enough to swallow legitimate rounding and it also swallows real typos/stale overrides; tight enough to catch real errors and it false-positives on every rounded dimension. Model it as a rounding-grid tolerance instead, using the dimension's resolved tier (`setout_critical` or `default`):
  - `rounding_grid(dimension)` + a small `measurement_epsilon` (~0.5–1mm, covers export/plot noise). Pass if `abs(stated − raw_drawn) ≤ rounding_grid(dimension)/2 + epsilon`.
  - Secondary signal (confidence/severity, not a hard gate): check whether `stated` itself is close to a multiple of its tier's grid. A value that's off *and* isn't a clean grid multiple is more likely a genuine typo or stale override (left over from a prior model revision) than one that lands cleanly on the grid — surface that distinction on the Issue so engineers can triage.
  - Orientation-agnostic by construction — "raw" length is the Euclidean distance between the witness-line-snapped endpoints (§5a mechanics), so angled/skewed elements aren't a special case as long as the dimension-to-entity association itself is correct.
- **Survey tolerance (§5b, reconstructed vs. tabulated setout value):** driven by construction/survey achievability standards, not drafting rounding convention — but the rounding-override behavior still leaks in, because reconstruction walks a *chain* of individually-rounded dimensions, and every edge in that chain is by definition `setout_critical` (point 2 above), so it's the tight tier's grid that compounds here, not the general default. Each hop can carry up to `rounding_grid(setout_critical)/2` of legitimate rounding error, so a point reached via a long chain can accumulate real, non-erroneous deviation well beyond what a single-hop point would show. A flat survey tolerance over-flags long chains or under-flags short ones. Scale the allowance with path length instead — same shape as a survey traverse misclosure formula, e.g. `allowance = base_tolerance + per_hop_allowance × √hops` as a starting form, calibrated against real chains in `samples/` rather than picked blind. Where multiple paths reach the same point, prefer the shortest as primary (least compounding) — a genuine conflict between paths is still always its own Issue per point 5 above, never silently resolved by picking the "better" path.

Both stay project-configurable per CLAUDE.md's "tolerances must be configurable, never hardcoded" rule — the grid values here are this project's drafting convention, not universal constants, and should be confirmed (both the `default`/`setout_critical` split and their actual figures) against real Revit-exported sheets in `samples/` before locking in.

**Output:** an overlay showing the reconstructed structure on top of the original drawing, with mismatches highlighted at the specific location, plus a data table of every setout point: drawn value, tabulated value, delta, pass/fail.

This is genuinely hard in the general case (ambiguous dimension chains, missing datums, drafting shorthand). Recommend scoping the MVP to a well-defined structure type (e.g., a single retaining wall run, or a simple bridge abutment) with clear setout table conventions, then generalizing once that reconstruction logic is proven.

**The purpose of the geometry check, restated by the user 2026-08-17 — and it is narrower and more tractable than "reconstruct the bridge".** Manually this is the expensive item: a senior drafter spends 1-2 weeks getting the design inputs, independently reconstructing the structure and comparing. But the *reason* has shifted. Fully compiled models now exist in Navisworks/Revizto for clash detection, so the bridge's overall location is already confirmed by other means, and rebuilding from control lines matters less than it did. **The live problem is 2D details drifting from the model.** Some drafting teams don't use "live" sections — they draw setout details as static 2D linework to save time, and those always drift as the model changes. The geometry check exists to catch that quickly.

**Why drawn dimensions legitimately differ from the model by a few millimetres, and the two workarounds this produces.** Bridge geometry is curved, so it is hard to get sections cleanly perpendicular to the items being sectioned; dimensions taken from model elements land a few mm off. This is not sloppiness, it is unavoidable. Drafters resolve it two ways, and the two have completely different checkability:

1. **Overwrite the dimension text.** The override is the drafter's assertion of the intended value; `DimensionEntity.measurement` still carries what the model actually says. `geometry.dimension_consistency` compares them against the rounding-grid tolerance (`grid/2 + epsilon`, ~3mm) — which is precisely a "accept intentional cleanup, flag anything larger" test. **Checkable from the DXF alone.** Its 0-issue result on BR06 means every override was within a few mm of the model, i.e. the check passing, not the check being useless.
2. **Draw small witness lines on the section and dimension to those.** The dimension then agrees perfectly with the drawn line, so the DXF is **internally consistent while being collectively stale** — when the model changes, line and dimension drift together, still agreeing with each other. There is no discrepancy inside the file to find. **For this route the IFC is not one option among several; it is the only possible source of truth.**

This also explains a difference that first looked like two unrelated findings: BR06 is 54% overridden (252 of 470 dimensions) while a Flinders sample is 4.5% (2 of 44, none numeric). Same problem, different workaround, and only one of them leaves evidence in the file.

**A per-dimension classifier for which workaround is in play, confirmed 2026-08-17 on both clients.** Layer naming distinguishes model-derived geometry from drafted linework, and taking the layer of the geometry nearest each dimension's witness points classifies each dimension individually:

- BR06 sheet 101051: 44 of 60 witness points land on `D-BDGE` — a model category layer.
- Flinders sheet 360044: 50 of 52 land on `A-DETL-*` — detail linework. That sheet is entirely the hand-drawn case.

Useful as triage ("these sheets carry drafted setout details, those are live"), and it needs no IFC, no config and no per-client calibration, since the layer convention follows a recognised standard rather than a client's own naming. **But it is context, not a filter.** The user's position, and it is the right one: *assume nothing is trustworthy or you will be caught out* — people are lazy and inconsistent, an override can be wrong or stale just as a witness line can, and good drafting checks are slow precisely because everything has to be verified. So every dimension gets checked against the model; the classification only tells you how to interpret a discrepancy.

**Section and elevation views are the hard boundary, and the blocker is that the cutting plane is Revit-only knowledge.** Investigated directly 2026-08-17 and confirmed unrecoverable from the export: no section-marker blocks exist in any DXF inspected (inserts are piles, centrelines, break lines, title blocks, linked model references), so a marker is exploded lines and text with no rotation to read; the 55 section markers `extraction/references.py` does find carry tag, source position, target sheet and target view position, and **no cut-line geometry, direction or depth**; each tag appears once per sheet, so there is no second head to define the cut as a segment. Plan views are fine — an anchor plus coordinates gives the transform geometrically. Sections are not.

**The way round it is how humans read drawings: match the view title to the model element.** A section dimensioning a pile cap's depth can be checked against that pile cap's height in the IFC without knowing where the cut was taken — you only need to know *which element* is being sectioned, and the view title says so. Correspondence by name rather than by geometry, scoped to one project, where both drawing and model came from the same Revit source.

**Lexical matching alone is not sufficient — measured, not assumed.** Against Flinders' real view titles and IFC family names: `PILE LAYOUT - ABUTMENT A` → `Abutment_Pile Cap_RC_8 Piles` (correct, 2 shared tokens); `FOUNDATION LAYOUT` → `Structural Foundation_Pier Option 6` (**wrong** — it is on an abutment sheet, and a human disambiguates from that context, which is not in the strings); `ACCESS HATCH PLAN` → nothing (no IFC family name contains "hatch"; you need to know what an access hatch belongs to). One right, one confidently wrong, one blank. The failures are semantic, not tuning.

**No LLM is available, and this is settled, not an open question (user, 2026-08-17).** Company machines are locked down to the point where a local model cannot be installed, the organisation is ~50,000 people where blanket rules are the norm, and arguing for an exception is not a productive use of time. So this must be fully deterministic — PLANNING's earlier self-hosted-model answer (§10) does not apply either.

**The deterministic route, and why the human cost is acceptable.** Correspondence is needed **per view, not per dimension** — a section carrying twenty dimensions needs the view identified once, and all twenty become checkable. On a ~116-sheet set that is a couple of hundred views, most resolvable from a ranked shortlist (lexical overlap plus geometric plausibility) as a confirm rather than a decision. Crucially it also **amortises**: the view→element mapping is established once per project and reused at every subsequent issue, and drift checking is inherently repeated. So the cost is an hour or two at first issue and minutes thereafter, against 1-2 weeks each time. Plan views with an anchor need no confirm step at all. A bridge-terminology table (abutment, pier, pile cap, headstock, girder, bearing, plinth, wingwall, approach slab...) would shorten the confirm list further and is worth noting as *one-time domain knowledge shared across all clients*, unlike per-client label vocabulary — but it is optional and incremental, not load-bearing.

**Proposed alternative source of truth for the rest: an IFC export of the 3D BIM model (raised 2026-08-11, not yet built).** This firm's stated workflow is Revit-authored, exporting both PDF and DWG from the same source model (§1, §8) — Revit can also export IFC (Industry Foundation Classes, the standard open BIM interchange format) from that same model, which would carry actual 3D member geometry (positions, extents, sometimes structural framing/rebar depending on export settings) independent of any 2D setout table.

**Confirmed 2026-08-11 by the user (not yet by a real file — see below): IFC export is a routine, always-current output on this firm's projects, not a one-off.** It's used for clash detection throughout the project lifecycle (coordinated in Revizto), so unlike a setout table — which only exists where someone chose to tabulate one — an up-to-date IFC is expected to exist for essentially every project. This also gives the check a real stated purpose beyond catching drafting errors: project management already trusts the IFC (via Revizto's clash coordination); a drawings↔IFC consistency check lets them extend that same trust to "the issued 2D drawings actually match the coordinated 3D model," not just "the 3D model is internally clash-free."

The shape this check would take, once a sample confirms it's viable:
- Parse the IFC file (`ifcopenshell` is the standard Python library — not yet added to `requirements.txt`, and this old x86_64-under-Rosetta Python 3.9.5 environment's wheel-availability quirk (§10/CLAUDE.md's cryptography note) should be checked before assuming it installs cleanly) into member-level 3D geometry (position, extents, and ideally a stable identifier/GUID per element).
- Cross-check against the DXF/PDF-derived 2D geometry the same way §5b's other mechanics work: independently-derived value vs. an authoritative source, delta beyond tolerance is an Issue, always reporting both values, never silently reconciled.
- This wouldn't replace §5a (drawn-vs-stated dimension checks stay DXF-based, since IFC likely doesn't carry annotation/override text) or the setout-table cross-check above (still the right mechanic where a table exists) — it's an additional source for structure that has neither a `DIMENSION` override to check nor a setout table to reconstruct against.

**First slice built, 2026-08-12** (`extraction/ifc_source.py`'s `ingest_ifc(path) -> IfcModel`, `ir.py`'s `IfcElement`/`IfcModel`) — ingestion only, no check rule yet, once real `.ifc` files existed to calibrate against: `samples/BR06/T2DPAA-T2D-C3S-BR-M3D-100302.ifc` and `samples/BR08/T2DPAA-T2D-C3S-BR-M3D-100304.ifc` (both IFC4, `ifcopenshell` installed cleanly — a prebuilt wheel exists for this environment, no repeat of the `cryptography` build-from-source issue). **The user flagged something important before this was built, confirmed directly against both files: BR06 and BR08 are the same client project, so their metadata conventions match each other — that's evidence those two files agree, not evidence any of it generalizes to a different client's Revit export.** This shaped the whole module — see `extraction/ifc_source.py`'s docstring for the full account, summarized here:

- **Schema-general, safe to build on:** element typing via IFC4's own `IfcElement` base class + `PredefinedType` (schema enum) + `GlobalId` (schema GUID) — not a hardcoded whitelist. Confirmed necessary, not just cautious: BR06 (`IfcBeam`/`IfcSlab`/`IfcBuildingElementProxy`/`IfcBuildingElementPart`/`IfcRailing`, 132 elements) and BR08 (`IfcMember`/`IfcWall`/`IfcRoof` added, no `IfcRailing`, 934 elements) already have different class mixes despite being the same client — a fixed "expected structural classes" list would have missed real data one sample over. World-space geometry, read via `ifcopenshell.geom`, is also schema-general: confirmed its default (`CONVERT_BACK_UNITS` left `False`) normalizes to real metres regardless of a file's declared length unit — both files declare millimetres, geometry output still comes out at metre scale.
- **Firm-specific, real but NOT to build matching logic around:** every element's `Name` is a raw Revit "Family and Type: Tag" string (e.g. `"03_SFR_ACS_Abutment_CS:ABUTMENT EAST_BR06_3:5328892"`) in this firm's own family-naming convention (`T2D_`, `WGA22_`, `08_ADC_`, `DIT_` prefixes confirmed) — not IFC schema, kept only as a non-authoritative `display_name` for labeling. Property sets are a real mix of portable ones (`Pset_BeamCommon`, `Qto_BeamBaseQuantities`) and clearly firm-prefixed custom ones (`T2D_Project`, `T2D_QTO`, `DIT_Location`, `DIT_Asset`) — not read at all yet, since there's no way to tell which of a *third* client's property names would be the portable ones without another real sample.
- **The georeferencing gap, confirmed real on both files:** neither carries IFC4's schema-standard `IfcMapConversion`/`IfcProjectedCRS`. Instead, `IfcSite`'s raw placement offset — read directly, bypassing the geometry kernel — is `(278000000, 6129000000, 0)` mm on **both** files, i.e. 278,000m E / 6,129,000m N: real-looking survey-scale coordinates baked directly into the model, not an arbitrary Revit internal origin. Identical between BR06 and BR08 confirms this is one client's shared "Survey Point" convention (consistent with the user's caution), not something IFC guarantees generally — a different client could use `IfcMapConversion` properly, or an arbitrary origin with no real-world meaning. `ingest_ifc` therefore does NOT assume raw world coordinates are real Easting/Northing; `has_map_conversion=False` is the signal a caller must independently verify this before trusting it for a real-world cross-check. `IfcSite.RefLatitude`/`RefLongitude` (schema-standard, present on every `IfcSite`) is read as a coarser portable fallback — confirmed real but imprecise: BR06's decoded value is -34.9572° vs. sheet 101051's real title-block `sheet_latitude` of -34.94188°, ~1.7km apart, a project-wide reference not per-sheet precision.
- **Confirmed real: a DXF sheet export and IFC world space are not directly comparable, and there's no single fixed transform to find between them.** A DWG/DXF export is one sheet's paper-space view (a crop/viewport of a view, not model space) — confirmed by the user, who corrected an early draft of this plan that treated it as "still needs its own resolution," as if a single sheet↔model transform were the missing piece. It isn't: there may not be one fixed, discoverable transform at all. The right move (below) is to never compare DXF geometry to IFC directly.
- **Correction, 2026-08-12: an earlier version of this section wrongly claimed BR06's IFC model has no piles.** That came from sampling only 8 of 45 real `IfcSlab` elements during exploration — the user caught it (visible in Navisworks) and it was wrong. All 28 real piles are there, modeled as `IfcSlab`/`PredefinedType='BASESLAB'` (Revit's class choice, not an IFC-standard "pile"). Confirmed a fully schema-general way to find them anyway, with no reliance on that firm-specific class/name choice: a bounding-box shape heuristic (`max(dx,dy) < 2m` footprint, `dz/footprint > 3`) applied across every element regardless of class finds exactly the same 28 elements as a Name-text search for "PILE" — zero mismatches. Real pile geometry on this sample: 0.75m × 0.75m footprint, 10.55m tall.
- **First real check rule built and working, 2026-08-12: `geometry.ifc_setout_consistency`** (`checks/geometry.py`). Per the user's direction, it does NOT compare DXF geometry to IFC — it compares each sheet's already-*reconstructed* real-world point (`extraction/setout_reconstruction.py`'s `reconstruct_sheet`, which derives real Easting/Northing from the sheet's own printed setout-point origin + bearing + dimension chain, independent of both DXF sheet-local coordinates and the schedule) against the nearest pile-shaped IFC element, using the shape heuristic above. Both sides of that comparison are already in real-world coordinates by construction, so no DXF↔IFC transform is needed at all. Run end-to-end against the real sample (37-page PDF + sheet 101051's DXF + BR06's IFC): all 24 reconstructable piles matched their nearest IFC pile within the 10mm default tolerance, 0 issues — the 4 off-structure/barrier piles `geometry.setout_reconstruction` already can't reconstruct are correctly skipped (nothing to compare), not double-reported.
- **Worth knowing before running its tests inline:** `ifcopenshell.geom.create_shape` is genuinely slow per-element native geometry-kernel work on this environment — observed 130-210s for BR06's 132 elements alone; BR08's 934 elements longer still. See `tests/test_ifc_source.py`'s docstring.

Still open: BR08 has no known setout table yet (its PDF hasn't been ingested/surveyed for one), so `geometry.ifc_setout_consistency` is only real-data-calibrated against BR06 so far.

**Non-pile superstructure (deck, abutment beams) — a coverage check built 2026-08-15, a real magnitude/position cross-check still not.** `checks/geometry.py`'s `geometry.ifc_superstructure_coverage` adds two more schema-general shape heuristics alongside the pile one — `_is_thin_horizontal_plate` (deck-slab-like: large horizontal footprint, thin) and `_is_elongated_beam` (abutment-beam/headstock-like: similarly large footprint, noticeably thicker) — both calibrated against the same real BR06 IFC model. Real findings worth recording: the `IfcSlab`/`FLOOR` elements actually named "Deck Slab"/"Deck Asphalt" carry no direct geometry on this export (`Representation=None`) — they're assembly parents that decompose (`IsDecomposedBy`) into child `IfcBuildingElementPart` elements ("Concrete - Cast-in-Place Concrete", one per pour stage) that carry the real geometry instead; six of those, footprint 7.56-23.07m, `dz/footprint` 0.0106-0.0402. Sampling 4 of the model's 68 real `IfcBeam` elements (all the same Revit family, `"...ABUTMENT EAST/WEST_BR06_<n>"`) found a consistent, clearly separate shape band: footprint 10.51-13.32m, ratio 0.100-0.124. Run end-to-end against BR06's real, full IFC model (132 elements): 0 issues — both categories genuinely present, correctly found.

Deliberately a **coverage** check only — confirms whether the attached IFC model has *any* element of each shape at all, not a drawn-vs-modeled magnitude/position comparison like the pile rule. That's not an oversight; a real numeric cross-check needs an independently-derived real-world value to compare IFC geometry against (the role the setout table + reconstruction plays for piles), and nothing like that is confirmed to exist for deck/beam elements: an abutment-to-abutment span computed from reconstructed pile positions was considered as a proxy for deck length and rejected — a pile-centerline span isn't the same real-world distance as a deck length (backwall setback, bearing offsets), by an amount this project has no confirmed figure for, so any tolerance around it would itself be a guess. The real IFC data adds a second reason not to force a DXF<->IFC *name* match here: the schedule's `LOCATION` column says `"ABUTMENT A"`/`"ABUTMENT B"`, but this project's real IFC abutment beam names say `"...ABUTMENT EAST/WEST..."` — no shared vocabulary between the two conventions. **Resolved 2026-08-15, by geography rather than naming** — the user pointed out every sheet carries a north arrow, so a bridge's abutments can always be oriented to real compass directions; this project doesn't even need to read one off the page, since both sides of the comparison are already real-world coordinates. Confirmed decisively on sheet 2871051/BR06: the reconstructed schedule points grouped by `LOCATION` give a real mean Easting per abutment (`"ABUTMENT A"` 278437.35mE, `"ABUTMENT B"` 278445.23mE), and the real IFC abutment-beam elements' own world-space centroids give the same figure directly (`"...EAST..."` beams average 278445.22mE, `"...WEST..."` beams average 278437.34mE) — sub-0.1m agreement against a ~7.9m abutment separation, so `A = WEST`, `B = EAST` on this project, derived rather than asserted. The mechanism is schema-general (real Easting vs. real Easting, no reliance on either side's naming convention), so it also answers `geometry.ifc_setout_consistency`'s own documented "no confirmed IFC-side location signal to scope by" gap, not just this rule's — and **is now wired into that rule's matching, same day**: `SetoutReconstructionPoint` grew a `location` field, and `checks/geometry.py`'s `_location_centroids`/`_nearest_location` scope the pile-matching rule's one-to-one greedy assignment to a point's own LOCATION group whenever the schedule has one (unscoped, unchanged behavior otherwise) — see that rule's docstring for the mechanics, and the real end-to-end confirmation that it doesn't change either sample's actual output (BR06's real, full IFC model still gives 0 issues), since ~8m real abutment spacing was already outside the 2m match radius either way; this is robustness for a future tighter-spaced project, not a fix to a live bug on the current samples. Matching a specific DXF `DIMENSION` to "the" overall deck length with no schedule/label to anchor on would repeat §1's PDF-dimension-reconstruction mistake (proximity-only matching silently picking the wrong candidate) in DXF instead of PDF — not attempted without first exploring real sheet data, and this doesn't touch that half of the gap. So: the naming-mismatch half of the original blocker is now closed (and wired in); the magnitude-correspondence half (above) stays open. Also still open: not yet re-confirmed against BR08 (its IFC model is far larger, and `ifcopenshell.geom` is genuinely slow per complex element — the deck-pour elements above, in particular, took close to two minutes each to mesh on this environment).

**The deck-magnitude half is resolved as out of scope, confirmed by the user 2026-08-15 — not a gap to close, a boundary this tool doesn't need to cross.** Deck geometry/design is the roads team's responsibility, not this tool's — so there's no real requirement to cross-check deck magnitude against anything here, which is exactly why no independently-derived comparison value was ever found: it isn't this team's data to reconcile. The coverage-only check (does the IFC model have a deck-shaped element at all) is confirmed as the intended final form for the deck half of this rule, not a stepping stone. Real, separate fallback the user also flagged: **if** the roads team hasn't done the deck design for a given project, a deck setout table exists and could be compared against the same way piles are — a real, potential future data source, not built (no sample to calibrate against yet), and only relevant in that specific "roads team hasn't done it" case.

**Abutment beams are a different story, confirmed by the user 2026-08-15 — still this tool's responsibility, genuinely open, and now better-scoped.** Unlike deck, beam geometry isn't the roads team's — this tool should be checking it. The originally-speculated "deck-length-style" magnitude proxy was the wrong shape of check anyway: the critical thing to verify is beam *placement*, specifically real-world **height/elevation** (bearing seat / soffit level), not a length or span comparison. A steel-girder superstructure (this sample's is concrete) comes with more/different detail drawings — a real project-type variable not accounted for yet. Not buildable yet — the user is getting a real sample to calibrate a height-based check against, same "wait for real data" discipline as everywhere else in this codebase, not guessed at ahead of that.

### 5c. Direction change — the checks move into Revit (2026-08-17)

**Decided by the user after the pause above.** Everything in §5 up to this point is an attempt to recover, from an export, information that exists in full in the authoring tool. The PDF/DWG route was chosen because that is what the team traditionally reviews, and the IFC was added later as a source of truth — but the model was the source of truth all along. The checks move into Revit as a pyRevit toolbar (`extensions/RevitCheck.extension/`). Scope is confirmed as **internal projects only**, so a model is always available; the "you can only check what you have a model for" objection does not apply.

**This dissolves the blocker rather than relocating it.** §5's hard boundary was that section and elevation cutting planes are Revit-only knowledge, unrecoverable from the export — and the workaround being designed was a ranked shortlist plus a per-view human confirm, because lexical view-title matching measured one right, one confidently wrong and one blank. Inside Revit, `ViewSection` carries its own origin and direction, and a `Dimension`'s `References` resolve to real element ids, so the correspondence question is a lookup. The no-LLM constraint stops mattering: nothing here needs semantic matching.

**Why it should generalise better, not just be easier.** §5's own Flinders finding was that logic built on domain invariants held across clients while logic built on client conventions broke. The Revit API is an invariant. `Element.ViewSpecific` replaces the CAD-layer proxy (`D-BDGE` vs `A-DETL`) that stood in for "is this drafted linework?"; `sheet.SheetNumber` replaces three title-block extraction strategies with synonym tables and prominence tie-breaks; `OfClass(RevisionCloud)` replaces scallop-arc vector clustering; `FamilyInstance.Location.Point` plus shared coordinates replaces the bearing + chained-dimension walk *and* the `IfcSite`-says-Massachusetts problem.

**What §5a becomes.** The two drafting workarounds for non-perpendicular sections stay exactly as characterised above, and the distinction still matters — but both become directly observable. `Dimension.ValueOverride` sits next to the model's own `Value` with no DXF export in between (workaround 1), and whether a dimension measures model geometry or view-specific linework is a property lookup rather than an inference (workaround 2). `revit.dimension_provenance` covers the second (2026-08-17) and `revit.dimension_override_consistency` the first (2026-08-18) — the latter is a direct port of §5a's rounding-grid comparison, and needed no new adapter code, since Revit hands over `ValueOverride` and the model's own `Value` on the same segment in millimetres. It also closes a gap §5a had: a client whose overrides are never numeric got a clean-looking zero-finding result from a rule that checked nothing, so the Revit version always reports how much was in scope. The check that verifies *drafted* dimensions against the model is sequenced next, and consumes the provenance rule's per-view output.

**What it does not change.** The standing position that classification is triage, not a filter — *assume nothing is trustworthy or you will be caught out* — is unaffected, and is why the provenance rule reports that the file cannot answer a question rather than that a dimension is wrong. Multi-hop survey-tolerance scaling remains open and still awaits a retaining-wall sample.

**What it removes from the plan.** §1's web stack, §2's stateless-by-design purge machinery, §7/§8's markup export as the delivery mechanism (a check that runs where the fix happens can select and zoom the element instead), and §11's purge-timing question. §10's offline constraint is satisfied trivially. BACKEND_REVIEW.md §8's API/DB/queue/frontend — "the majority of the work" — is no longer on the path.

`src/pdfchecker/` was left in place for the pivot itself — the decision was to stand the Revit path up first and converge afterwards, rather than refactor a working, tested package mid-pivot — and was **parked on 2026-08-18** once that path was standing: tagged `pdf-dwg-final` and removed from the tree, with the glossaries and the en-GB variant list rescued into the live tree because their content is hand-made judgement. See `ARCHIVE-pdf-dwg.md` for the full account and `extensions/RevitCheck.extension/README.md` + CLAUDE.md for the built state.

### 5d. Revit 2026, and the reporting decision (2026-08-18) — BCF

**Platform.** Work continues in **Revit 2026**. pyRevit 5.1.0 is the release that added 2026 support (.NET 8); the buttons already carry the `#! python3` shebang selecting the CPython engine, and CI already gates 3.12, so no version work is expected. `adapters/revit_source.py`'s `_eid` already prefers `ElementId.Value` over the `IntegerValue` deprecated in 2024, which is the usual source of version breakage.

**The reporting question is open.** §5c retired §7/§8's markup export on the grounds that "a check that runs where the fix happens can select and zoom the element instead", and `output.linkify(ElementId)` in the pyRevit output window has been the delivery mechanism since. What that does not give is **persistence** — nothing survives closing the output window, so there is no record of what was reviewed, what was accepted as intentional, or what was dismissed as a false positive. That gap is what reopened the question.

**Autodesk Forma issues were proposed as the answer and are a candidate, not a decision.** The user's position is that report output should be worked through — several options rendered and compared — before committing. Research done 2026-08-18, recorded here so it is not repeated:

- **The Forma Issues API cannot create element-pinned issues.** Autodesk's GA documentation states plainly that *"Document specific issues (a.k.a. pushpin issues) are not supported"* and that *"Issues API supports 3-legged authentication only."* The `linkedDocuments` field — which carries exactly what would be wanted, `details.objectId` (the element id), `details.externalId` (the element GUID), `details.position` and `details.viewable` — exists in the schema but is **not writable on creation**. Pushpins are placed by a human in the Docs viewer or the Revit Issues Add-in, not by an API client.
- **What an API-created issue *can* carry** is the full workflow object: `title` and `description` (10,000 chars each), `status`, `issueSubtypeId`, `assignedTo`/`assignedToType`, `dueDate`, `watchers`, `rootCauseId`, `customAttributes`, and `locationDetails` as free text (8,300 chars). So it can be assigned, dated, tracked and closed — it simply has no notion of *where*.
- **The Revit Issues Add-in requires Revit Cloud Worksharing.** Autodesk documents that issues are not visible in locally-workshared files opened through Desktop Connector. Not a constraint for this firm, whose models are cloud-workshared, but it is a hard one for anybody else's.

**Why this is a genuine trade rather than an upgrade.** Element-level targeting is the core of this project's Issue model — `issue.py`'s docstring is explicit that the whole point of the pivot was that "a location is an `element_id`" which pyRevit turns into a click-to-zoom link, and that §8's markup apparatus existed to bridge a gap that no longer exists. Filing findings as project-level Forma issues trades that away for tracking and for visibility to people without Revit. That may well be worth it — but it is a trade, and the decision should be made from rendered examples rather than in the abstract. Other candidates to compare: a richer in-Revit output, a standalone HTML report, BCF export (element-pinned via viewpoints, and an open standard), and a plain CSV review register.

**Decision: BCF, taken 2026-08-18** after rendering all six candidates side by side with real output from the three built rules. The comparison is what settled it — the options were argued in the abstract first and it did not resolve; seeing them did.

**Why BCF wins on this project's own terms.** It is the only off-machine format that keeps the element anchor. A BCF `Component` carries both an `IfcGuid` (for every other tool) and an `AuthoringToolId` (which can hold the raw Revit element id, so a BCF opened Revit-side lands back on the exact dimension). Every other persistent option — HTML, CSV, Forma issues via API — degrades the location to a number a human retypes into Select by ID. Given that §5c's whole argument for moving into Revit was that "a location is an `element_id`" the tool can select and zoom, a delivery format that throws that away would be spending the pivot's main winnings.

It is also **vendor-neutral and offline**, so it survives whatever Autodesk does to its APIs — which matters more than usual here, given that the Issues API's inability to write `linkedDocuments` is precisely the kind of platform limit that made the PDF/DWG route painful.

**The Forma leg is real but not yet GA — plan accordingly.**

- **BCF *export from* Forma/ACC is generally available**, carrying comments, image attachments, selected model elements, camera view and thumbnail, capped at 250 issues per file, for RVT and IFC.
- **BCF *import into* Forma/ACC is in beta.** Announced "coming soon" in the September 2025 release notes and still described as a limited beta programme through 2026, requiring Manage permission or higher. Model Coordination's Navisworks path is documented as *not* supported, with BIMcollab's Navisworks add-in given as the workaround.

So the Forma round trip is an **upside arriving on Autodesk's schedule, not a dependency**. BCF earns its place on day one through Navisworks/Solibri/BIMcollab/Revizto, and if import goes GA the same file flows in unchanged.

**What this means for the build.** BCF needs a durable per-element identifier, which the IR does not currently carry — see the `unique_id` addition in the adapter work. That field was already justified independently as the identity that survives model versions; this decision makes it load-bearing rather than insurance. Target **BCF 2.1** as the widest-supported version (confirm against the tools actually in use before committing). `report.py` gains a sink alongside `to_json`/`to_markdown` rather than being restructured — the issue list and its rendering are already separate.

**Not chosen, and why it is still worth doing:** the richer in-Revit output (grouping, severity chips, coverage promoted out of the trailing position) solves *reading* rather than *remembering*, and remains the cheapest real improvement to the working loop. It is complementary to BCF, not an alternative — findings get triaged in Revit where click-to-zoom is native, and BCF carries out what survives.

## 6. Client specification check

**Probably not needed — confirmed by the user 2026-08-15, downgraded from "deferred pending a real sample" to "unlikely to be worth building at all."** Recorded here rather than deleted, per this doc's own convention of keeping a trail of *why* a decision changed (§1, §4, §11). Revisit only if a real, concrete need for it actually shows up — not a default assumption anymore the way the rest of this section below still describes it.

Client-supplied specification documents (project specs, not just drawings) encode requirements that drawings must satisfy — minimum concrete cover, factor-of-safety values, bar spacing, mandated terminology, material grades — and firms currently check these by hand. This feature extracts those requirements and auto-generates rules that feed the two engines above (§4, §5), rather than being a separate third engine with its own IR.

**Input:** client spec as PDF or Word (DOCX). Real specs are a mix of narrative clauses (CSI-style sections, prose requirements) and embedded tables/schedules of numeric limits — the extractor has to handle either, not assume one format.

**Extraction pipeline**
```
Spec upload (PDF/DOCX)
  -> Text + table extraction (PyMuPDF/pdfplumber for PDF, python-docx for Word)
  -> Clause segmentation (section/clause numbering, headings)
  -> Requirement extraction (self-hosted LLM, see §9) -> structured SpecRequirement records
  -> Auto-registered as project rules, flagged as spec-derived
```

Each `SpecRequirement`: clause reference (e.g. `§03 30 00 3.2`), verbatim source text, extracted parameter/operator/value/unit where numeric (e.g. `cover >= 50mm`), applicability (element type/discipline the clause governs), and an extraction confidence score. These live alongside `Project`, not `Sheet` — a spec applies to the whole project, not one drawing.

**Two requirement kinds, feeding the two existing engines:**
- Narrative/presence requirements (e.g. "drawings shall note rebar as Grade 60", terminology the spec mandates) become drafting rule-catalog entries — same `(IR, config) -> [Issue]` shape as any hand-written rule in §4, just auto-generated.
- Numeric/threshold requirements (cover, spacing, factor of safety, dimensional limits) become geometry-engine parameter/tolerance overrides (§5) — checked against drawn or tabulated values the same way setout deltas are, except the "expected" value comes from the spec instead of a setout table.

**Auto-apply with flagging.** Extracted requirements go live in the active rule set immediately — no manual approval gate before they can flag issues on a check run — but every Issue raised from a spec-derived rule is visibly tagged (`Spec:` label prefix, e.g. `Spec: cover 42mm < 50mm required`) and carries its clause reference and extraction confidence, so an engineer can immediately see which flags came from automated extraction and prioritize checking the low-confidence or unusual ones. A spec review screen lists every extracted requirement (source clause, generated rule, confidence) so a misextracted rule can be corrected or disabled —**within the same session, before the final report/markup set is generated** (§2's "Stateless by design" — there's no persistent project to come back to later and revise), then the engineer re-runs checks against the corrected rule set before downloading.

**Markup/report integration:** spec-derived issues use a `Spec: <what's wrong>` note in §7's markup table and carry the clause reference as their report backlink, the same role a rule ID plays for other issues.

**Scoping note.** Free-form narrative extraction is open-ended NLP; recommend scoping first to the numeric/threshold case (structured schedules, clearly stated single-value limits) since it's highest-value and least ambiguous, then extending to narrative/presence requirements once extraction quality is proven against a real client spec sample (see `samples/` conventions in CLAUDE.md — the same "check real documents before assuming a format" principle applies here).

**Flow**
1. Check run completes → issue list (as in §7), each already tied to a sheet and a location.
2. Engineer selects which issues to include (default: all; filterable by severity/category/sheet — e.g. exclude a low-severity spelling flag they've decided to ignore).
3. "Generate markup set" renders each selected issue directly onto its sheet, at the issue's recorded location.
4. Output is a downloadable marked-up PDF (plus the §7 report), ready to send straight to drafting. One artifact, not a format choice — see the DXF/DWG removal note above.

**Keep markups minimal.** A sheet with twenty issues is unreadable if every one gets a full-sentence description. Each markup is two elements only:
- A **box** drawn tight around the flagged content's bounding box (not a cloud — clouds are for freehand engineer markup, not something worth simulating; a precise rectangle is faster to read and cheap to generate from the Issue's stored bounding box). Use a bounding-box-less marker (small circle at the point) only when the issue is an *absence* — nothing exists yet to box, e.g. a missing dimension.
- A **leader to a short note**, one line, `Label: payload` — a fixed short label per rule category plus the minimum information needed to act, no restated description:

| Category | Note format | Example |
|---|---|---|
| Spelling | `Spelling: <correct word>` | `Spelling: concrete` |
| Missing dimension/annotation | `Missing: <what>` | `Missing: dimension` |
| Unresolved callout/cross-sheet ref | `No match: <ref>` | `No match: Detail 4/S-402` |
| Revision inconsistency | `Rev: <what's wrong>` | `Rev: cloud has no table row` |
| Standards/convention | `<field>: <expected>` | `Layer: should be C-WALL` |
| Dimensional consistency | `Drawn <a> ≠ dim <b>` | `Drawn 3.42 ≠ dim 3.40` |
| Geometry/setout mismatch | `Setout Δ<value>` | `Setout Δ0.015` |
| Client spec mismatch (§6) | `Spec: <what's wrong>` | `Spec: cover 42mm < 50mm` |

Every rule in the catalog defines its own note template alongside its check logic (not a generic description field), so the label is always predictable and the payload is always the smallest thing a drafter needs to make the fix.

Markups can stay this terse because they're not the only output: each issue gets a short reference tag (e.g. `#014`) printed after its label, and the full report (§7, exported alongside the marked-up set) has the matching entry with the complete description, rule (or spec clause) reference, sheet, and both drawn/tabulated values. The sheet answers "what to fix"; the report is there for "why" if the drafter or engineer needs it — most issues won't require anyone to open it.

1. **Sheet correspondence between the DXF/DWG set and the PDF set.** Confirmed workable against the real samples (not just assumed): `samples/dwg/`'s 31 files and the PDF's 37 sheets share a numeric suffix — DWG `T2DPAA-T2D-C3S-BR-DRG-101032_0.dwg` ↔ PDF sheet `2871032` (title-block `sheet_no`), matching on the last 4 digits, no exceptions across the set. A clean numeric join, not fuzzy title matching — though the DWG's own title-block/attribute data should confirm this once DXF parsing exists, rather than trusting the filename alone as the sole source.
2. **A per-*viewport* (not just per-sheet) DXF-space -> PDF-page-space transform.** Refined 2026-08-10 against real converted DXF: a sheet's paper-space layout typically contains *several* `VIEWPORT` entities (4-11 across the real sheets inspected, e.g. plan + multiple elevation/section views on one sheet), each independently windowing into model space at its own scale and center (`VIEWPORT.center`/`width`/`height` in paper space, `view_center_point`/`view_height` in model space — a real, derivable affine map per viewport, not a georeferencing problem, confirming the low-risk assessment below). **Consequence:** a geometry Issue's model-space location needs to be matched to *which viewport* actually shows it before the transform can be applied — not one sheet-wide mapping. This is a materially different (harder) problem than originally sketched, worth building against a real converted-DXF-next-to-its-PDF-page pair (§9) rather than assuming a single sheet-level transform will do. Confirmed still low-risk overall: **this firm's workflow is Revit-authored, with each sheet view exported to both PDF and DWG from the same source** (user-confirmed, 2026-08-10) — so each individual viewport's PDF-page region and DXF model-space window should agree, it's just N transforms per sheet instead of one. **Built 2026-08-14** — `extraction/dxf_pdf_transform.py`; see §9's build-order item 3 below, and that module's own docstring, for the real calibration result (paper-space<->PDF is a fixed universal scale with no offset, and the per-viewport transform was validated end-to-end against real pile-label positions on two different real sheets).

**Suggested fix**
Not every rule can generate one automatically, but many can, and it's worth having the rule catalog populate this from the start rather than bolting it on later. The full-sentence description (shown in the in-app issue list per §7) and the terse markup note (above) are two different renderings of the same underlying fix data — a rule that can compute "concrete" as the correction, or "3.42 vs 3.40" as the delta, feeds both.

This means the `Issue` object (produced by every rule, `(IR, config) -> [Issue]`) needs: a precise location (point, bounding box, or entity handle, not just "sheet N"), a full description for the issue list, and — where derivable — a structured `suggested_fix` (e.g. `{corrected: "concrete"}` or `{drawn: 3.42, expected: 3.40}`) that the markup renderer turns into the short note. Rules without an obvious auto-fix carry a description but no `suggested_fix`, and get boxed with just their label (no payload). Build this into the Issue schema from the first rule written, even before the markup renderer exists, so it isn't a retrofit.

**Traceability — scoped back 2026-08-10.** This originally proposed tagging each markup with a persistent `issue_lineage_id` so a later re-check could automatically detect which flagged items were addressed vs. still open, turning this into a closed-loop QC cycle across runs. What remains: each markup still carries its per-run reference tag (`#014` above) linking it to its report entry, which is within-session and unaffected. ## 12. Direction change — pyRevit is a proof-of-concept host, not the production one (2026-08-21)

**Decided by the user.** pyRevit's CPython bridge (§5c moved the checks into Revit via pyRevit; nothing about §5c's reasoning for being *inside Revit at all* is affected here) has now failed the same way on two different machines. The 2026-08-19 debugging session (`extensions/RevitCheck.extension/README.md`'s "Three CPython gotchas") found three causes, all of them **environment-coupling problems, not code bugs**: `pyrevit.forms` being IronPython-only under `#! python3`, pyRevit's Reload permanently breaking the in-process Python runtime until Revit restarts, and the CPython engine needing an exact Python version match to even start. On 2026-08-20, sharing the `DimensionProvenance` button with a colleague reproduced the same class of failure on their machine. Two machines, same causes: this is pyRevit's CPython-hosting model itself, not a one-off local misconfiguration worth another round of troubleshooting.

**What changes.** Production deployment moves to a compiled, native Revit add-in (a `.addin` manifest plus a .NET DLL, loaded by Revit directly) rather than pyRevit script buttons. A compiled add-in either loads or it doesn't — there is no Python engine version to match and no in-process runtime to break on reload, which is the actual mechanism behind all three of the 2026-08-19 causes.

**What doesn't change.** §5c's argument for being inside Revit at all — that section/elevation cutting planes and dimension references are Revit-only knowledge, and that the Revit API is the invariant that survived contact with a second client where CAD-layer conventions didn't — is about *where the checks run relative to the model*, not about pyRevit specifically. None of that is affected. Nor is the layering CLAUDE.md defends (`adapters/revit_source.py` is the only Revit-API-importing module; `ir.py`/`checks/*.py` are plain Python) — if anything, a native add-in needs that boundary respected even more strictly, since the "extract facts, judge nothing" adapter is what stays swappable underneath a rewritten host shell.

**The real cost, and the decision inside this decision: what happens to the Python rule engine.** `checks/dimensions.py`, `catalog.py`, `ir.py` — the tested, stdlib-only `revitcheck` package that `capture.py` exists to let anyone develop against off a Revit machine (CLAUDE.md: "the workflow rather than a convenience feature") — is Python. A native add-in is (idiomatically) C#/.NET. Three ways to reconcile that, evaluated here rather than defaulted into:

1. **Port the checks to C#.** Not untestable in principle — the same pure-core/thin-adapter split works in C# too (a Core class library of plain POCOs + check logic, unit-tested with xUnit/NUnit via `dotnet test`, which is cross-platform), so this is not "Python can be tested and C# can't." The real cost is that it is a full rewrite: all 131 existing tests and the logic behind them get re-written and re-verified from scratch, with real risk of subtle translation bugs (float formatting, iteration order, string handling) that simply don't exist if the working, already-tested Python stays as it is — and if the Python version keeps running alongside it for any reason rather than a clean one-time cutover, that's real, ongoing drift risk between "what got tested" and "what runs in production," for no benefit this project has asked for.
2. **Embed Python in the add-in via pythonnet**, the same mechanism pyRevit uses internally. This reconstructs the exact failure this section exists to get away from — the add-in would now own the CPython-version-matching and runtime-init fragility that pyRevit owned before, just under different branding.
3. **Keep the rule engine exactly as-is in Python; the add-in shells out to a real `python.exe` subprocess** running `scripts/check_capture.py` against a JSON extraction — the same command already run from a terminal today, just invoked by the add-in instead of by a person. No embedded runtime in the Revit process, so nothing to break on reload; the add-in's job shrinks to extraction, invoking the subprocess, and writing the BCF result back.

**Decided by the user, 2026-08-21: option 1, a complete port.** The initial recommendation here was option 3, on cost grounds — cheapest, and the existing test suite survives untouched. The user's counter-argument is the right one for this project's actual failure history: option 3 still leaves a live external-runtime dependency on every deployed machine (a Python interpreter, bundled or firm-managed, that has to be *present and version-matched* before the add-in can run a check at all) — which is the same shape of problem that has now broken deployment twice (§12's opening paragraph), just moved from "pyRevit's CPython engine" to "the subprocess's Python." Option 1 is the only one of the three with **zero external runtime dependency**: a compiled add-in with no Python anywhere either loads or it doesn't, with nothing left to version-match at install time on a colleague's machine. For a tool meant to reach multiple users rather than stay a single-machine proof of concept, that is worth more than the rewrite cost — long-term deployment stability over near-term build time, in the user's own words.

**What this costs, concretely, and how to spend it well.** Every one of the 131 pytest tests (and the `checks/dimensions.py` / `catalog.py` / `ir.py` logic behind them) needs an equivalent, independently-verified xUnit/NUnit counterpart in the new Core library — this is translation risk, not a formality, so the port should go rule-by-rule with the existing Python behaviour as the spec to match, not a memory of what it does. The pure-core/thin-adapter boundary (§"What doesn't change" above) is what makes this tractable at all: only the adapter touches `RevitAPI.dll`, so the Core library's tests can run anywhere `dotnet test` runs, including this Mac, mirroring today's capture/pytest loop rather than losing it. `capture.py`'s JSON schema is worth keeping identical in the C# port (or at minimum trivially convertible) so the one real capture already collected (`samples/T2DPAA-T2D-C3S-BR-M3D-100304_Peter.capture.json`) stays usable as a C#-side test fixture rather than needing a second Revit-machine trip to re-capture it.

**Not yet decided:** whether the Python `revitcheck` package is retired once the port is verified equivalent, or kept around as the offline dev/reference implementation the C# port is checked against. Worth answering before the port starts, since it changes what "done" means for the C# test suite (matching Python's behaviour once vs. staying in permanent lockstep with it).

**What this means for sequencing.** The current pyRevit extension stays frozen in scope — no new buttons, no growing surface — and is used only to prove the Revit → BCF → Forma → Revit round trip once. That proof needs the BCF v2.1 writer and the `unique_id` adapter field regardless of which host ends up running the checks in production (§5d), so that work is unblocked and unaffected by this decision and should proceed against the pyRevit extension as it exists today. The native add-in is the project that follows the proof, not a prerequisite for it.

**The round trip is proven, 2026-08-22 — pyRevit's job here is done.** Four real Forma import attempts, each failure diagnosed from the exact error text rather than guessed at: `.bcfzip` rejected outright ("file must be in bcf format" — an extension check; renamed to `.bcf`), then "empty" (missing `project.bcfp` and a camera, both added), then "no viewpoint file found for one or more BCF topics" (one coverage finding had no Viewpoint at all under the original design; every Topic gets one now), then the same error again with files that *did* have viewpoints (the real bug: `<Viewpoints Guid="..." Viewpoint="viewpoint.bcfv"/>` was an invented attribute form — the actual BCF shape is a `<Viewpoint>` child element). The fifth attempt imported successfully. A follow-up warning ("some issues... not linked to a model element or may not match the current model") led to a further change — anchoring findings to their sheet (`SheetInfo.unique_id`) rather than the dimension/view element itself, since neither has 3D placement for a model viewer to resolve, still to be confirmed against a fresh capture.

**Confirmed by the user, 2026-08-22: this is all pyRevit needed to do.** No further pyRevit feature work is planned. `revit.dimension_provenance` and `revit.dimension_override_consistency` stay as they are — triage, not verification, and known to over-flag (see the next paragraph) — rather than being tuned further in this host. The native add-in is next.

**What the add-in actually needs to build, restated by the user 2026-08-22.** Today's session spent real effort narrowing `dimension_provenance`'s volume (rollup threshold, drafting-view scoping, reinforcement-sheet exclusion) and every bit of it was treating a symptom. The rule's own docstring already says so: it reports "triage, not verdicts" — that the file can't answer whether a dimension is right, not that it's wrong. A dimension drafted to a witness line, or overridden with a bar mark instead of a number, is not a problem *because* it's drafted or overridden — bridge geometry (curves) and drafting practice (needing "clean" issued drawings) mean that will always be true of some dimensions, permanently, not a defect to filter away. It is only a problem if the drafted/overridden value has actually **drifted from what the model now says**. That comparison is the thing this project has not built since the pivot into Revit — and it is not a new problem: it is the same one `geometry.ifc_setout_consistency` solved in the parked PDF/DWG pipeline (this section, above — a real IFC-vs-reconstructed-setout comparison, calibrated against BR06, 0 false positives on 24 real piles matched within 10mm). That capability worked. It simply didn't survive the pivot, because §5c's argument for moving into Revit — "the model is already the source of truth" — never got followed through to actually comparing against it.

**One genuine simplification versus the old IFC approach: no intermediary is needed anymore.** The old pipeline compared an *export* (PDF/DXF) against IFC because it had no other access to ground truth. Running inside Revit, the ground truth is the live model itself, one API call away — not a separate file to parse, with its own coordinate system and export-timing staleness risk to reconcile. Re-measuring a dimension's witness points against current model geometry inside the same session that read them is a strictly easier version of the same problem, not a harder one. This is exactly the work CLAUDE.md's "Next" section already names ("verify drafted dimensions against the model... witness points in model space, the view's own cut plane and direction, nearby model elements") — it now has a firm home: the native add-in, not pyRevit, and not before it.

**A limitation worth stating plainly.** Nobody on this side of the work has Windows, Visual Studio, or the Revit SDK. A C# add-in gets written the same way `adapters/revit_source.py` already is — blind, compiled and debugged only at the Revit machine — except that now applies to the whole host shell (ribbon/panel registration, `IExternalCommand` handlers, the `.addin` manifest, assembly loading and versioning) rather than just the read-only extraction logic. Expect more iteration cycles at the Revit machine than the Python side needed, not fewer.

## 15. First real add-in run against a cloud model found a real bug (2026-08-25)

Running Metadata Reconciliation against a real **cloud-shared** model (Revit Cloud Worksharing — BIM 360 / Autodesk Construction Cloud / Autodesk Docs) crashed writing the output file: `NotSupportedException: The given path's format is not supported.` Same lesson §13 already drew, applying again to a different corner of the same command: **a first real run finds real bugs review doesn't**, and this is genuinely a different bug shape than §13's three (those were comparison-logic bugs; this is an I/O/environment one).

**Cause:** `Document.PathName` for a cloud-hosted model isn't a filesystem path — it's a URN-shaped string (`"BIM 360://ProjectName/Model.rvt"`, or similarly for Autodesk Docs). The code only guarded against `PathName` being *empty* (a document never saved locally); a cloud model's `PathName` is non-empty and genuinely unparseable as a path. .NET Framework's `Path.GetDirectoryName`/`GetFileNameWithoutExtension` throw on the `"://"` — any colon outside the drive-letter position is invalid under the classic Windows `Path` implementation the add-in runs under (net48, inside Revit). Confirmed this does **not** reproduce on this Mac's .NET 8 — its cross-platform `Path` implementation is far more lenient about the identical string — a real platform-behaviour gap worth remembering before trusting a `Path.*` sanity check run anywhere but the actual net48/Windows target.

**First fix attempt didn't clear it — the real bug was one layer up.** The first `DocumentPaths.cs` wrapped `Path.GetDirectoryName`/`GetFileNameWithoutExtension` in a try/catch but read `doc.PathName` itself as a bare, unguarded argument expression at the call site. Deployed and re-run: identical error, on Metadata Reconciliation *and* the brand-new Dimension Provenance/Overrides (which had never touched this code before, ruling out a stale-build explanation). The actual failure is one layer earlier than assumed — either the `PathName` *property getter* itself throws for a cloud model (plausible: the exact .NET Framework `NotSupportedException` message text is what internal path normalization throws, and a getter could easily trigger that before ever handing a string back), or something downstream of the parse that wasn't wrapped either. Genuinely couldn't pin down which without a Windows/net48 machine to test against directly — worth being honest that this was diagnosed from a second real error report, not confirmed by reproducing it locally.

**Fixed properly, and more robustly, 2026-08-25 (second pass):** rather than keep guessing which exact call throws, the three check-producing commands (Metadata Reconciliation, Dimension Provenance, Dimension Overrides) now **prompt for a save location via dialog**, the same `SaveFileDialog` UX `CaptureModelCommand` already had — sidestepping `doc.PathName`-derivation entirely instead of trying to out-guess it. Requested by the user directly, having seen Capture Model's dialog and asked why the others didn't have one — it turned out to also be the more robust fix. `DocumentPaths.cs` now only supplies a safe *suggested* filename for that dialog, with every property read (`PathName`, `Title`) wrapped individually rather than assumed safe. `dotnet build` clean, all 243 tests still pass (Addin-side, untestable off Revit like the rest of that layer) — still needs the Revit machine to confirm this clears the real cloud-model run, but the design no longer depends on correctly guessing Revit's cloud-path behaviour at all.

## 17. Dimension provenance noise: overridden Drafted/Mixed dimensions, and a real `is_overridden` bug underneath it (2026-09-02)

**Real user report, first day of using the checklist window on real triage volume:** the combined `revit.dimension_provenance` + `revit.dimension_override_consistency` triage was flagging overridden dimensions used to label barrier extents as "measures detail linework, may have drifted" — real noise, not a real drift risk, because an override fixes the printed value by hand and can't silently drift the way an unoverridden drafted dimension can. **A second, independent real bug surfaced investigating dimension `9103358`'s blank override.** `DimensionSegmentInfo.is_overridden`/`IsOverridden` was `bool(self.value_override)` / `!string.IsNullOrEmpty(...)` — true for content, **false for an empty string**. `_text_or_none`/`TextOrNone`, applied uniformly to `Prefix`/`Suffix`/`ValueOverride`, collapses Revit's own empty-string-for-unset convention to `None` — correct for `Prefix`/`Suffix`, wrong for `ValueOverride`, where Revit's "Replace With Text" checkbox ticked with nothing typed is a *deliberate* blank override, not "never touched". The real captured data for dimension `9103358` (already sitting in the committed sample capture, predating this fix) settled what Revit actually stores for that case: `value_override: "‎"` — a single invisible LEFT-TO-RIGHT MARK character, not `""`. So the specific empty-string collapse was not the mechanism keeping this dimension flagged (a lone U+200E is truthy either way) — but the *general* bug (real blank overrides silently indistinguishable from "no override" for any project where Revit really does return a bare `""`) is real and was fixed anyway: new `_value_override_text`/`ValueOverrideText` helpers preserve Revit's null-vs-empty distinction for `ValueOverride` specifically, `is_overridden`/`IsOverridden` now check `is not None` rather than truthiness, and both are exercised in new regression tests using the real U+200E text, not a synthetic empty string, so a future regression of either bug would actually be caught.

**Validated three ways, in order:** (1) synthetic checks of all four shapes (plain override, real U+200E blank override, MIN/MAX bound, no override) confirmed the suppression logic directly; (2) the real committed capture's dimension `8199083` turned out to predate the override being added to the live model (`value_override: null` in that snapshot, `value_mm` matching the user's stated 114.779mm exactly) — good corroborating evidence of the right dimension, but the override itself couldn't be end-to-end verified against this stale file, hence (1); (3) the real-capture parity test (`RealCaptureParityTests`, the strongest available check against C#/Python translation drift) was regenerated against the live Python engine twice — once for the Drafted-only cut (957→943 issues), once more after extending to Mixed (943→928; 894 provenance + 34 unchanged override-consistency, 855 high/72 medium/1 low) — and both times the C# engine's own output matched the regenerated Python fixture exactly, issue-id for issue-id. 172 Python tests passing (166 + 6 new), 332 Core tests passing (326 + 6 new).

**Same session, a second, independent real request: Element IDs shown in the checklist window's details pane required manually retyping into Revit's own Select-by-ID search box.** Two new buttons on the details toolbar: **Select in Revit** (new `SelectElementsExternalEventHandler`, the same `IExternalEventHandler` pattern `OpenViewExternalEventHandler` already established — `UIDocument.Selection.SetElementIds`/`ShowElements` both verified against the real `RevitAPI(UI).dll` via `MetadataLoadContext` before writing any code) and **Copy Element ID(s)** (a plain `Clipboard.SetText` call, no Revit API context needed, kept as a fallback for pasting outside Revit entirely). `dotnet build` clean across the whole solution including the net48 Addin. Like every other Addin/WPF-only change in this codebase, this cannot be exercised by an automated test off the Revit machine — needs a real run to confirm, same discipline as everything else in this document.

**Same session, a third real report, investigated and deliberately left unfixed: spot coordinates/elevations showing up in the same triage list.** On the real committed capture, 6 of 347 spot dimensions (`SpotDimension` — Coordinate/Elevation/Slope) generate a `DRAFTED` provenance Issue, all on Abutment/Deck/Service-support general arrangement plans (sheets 2873062–64, 2873121, 2873251) — exactly the deck/abutment element type named as this project's next area, not a stray coincidence. Confirmed by the user: unlike a linear `Dimension` (whose References genuinely are the witness geometry the printed length equals), a `SpotDimension` often can't snap directly to the model geometry it's reporting a position for — a Revit tool limitation, not a drafting choice — so a drafter snaps it to a manually-placed `DetailLine` (or, real data shows, a view-specific `FamilyInstance` — almost certainly a Detail Component symbol used as the same kind of placement anchor) purely to get it positioned correctly. That makes the existing DRAFTED/MIXED classification mechanism (built for linear witness-point dimensioning) not really valid for a spot's References, since the reference doesn't determine what the spot's `Value` measures the way it does for a linear dimension.

**Decided, per the user directly, not to suppress this — the opposite of the override-noise fix above.** "If we build the tools to check the location of these it is fine, currently the pile tool does not and they all need to be cleared manually" — i.e. flagging a spot dimension here is legitimate triage, not noise, *because nothing yet verifies its real position against the model*. Suppressing it now (the way the override case was suppressed, where nothing could ever check it either way) would throw away a real, checkable finding rather than an uncheckable one — the honest state is "still open, needs a human to clear it," exactly what `CheckingSession`'s manual-verdict path already exists for. **Revisit this once a deck/abutment (or spot-coordinate-specific) investigation check exists** that can verify a spot's real position directly against the model, the same way the two pile checks do for piles — at that point deferring to the real check (rather than the reference-based provenance heuristic) becomes the right call, mirroring exactly how `revitcheck.pile_model_schedule_consistency`/`pile_chain_bearing_consistency` already made the older, weaker signal unnecessary for piles. No code changed for this one.

**Not yet run on the Revit machine.** Both the dimension-provenance suppression rule and the two new checklist buttons need a real run before being considered confirmed, matching this project's own standing pattern that every real correction so far came from an actual machine run, not code review alone.

## 18. Deck/abutments, started the same way piles were: real ground truth first (2026-09-02)

**Per the user's own direction: start the second element type (CLAUDE.md's "Also open" — abutment beam placement, real-world height/elevation, bearing seat/soffit level) the same way piles were.** That means the diagnostic-first discipline (PLANNING.md §14), not writing comparison logic ahead of a sample — the repeated lesson named throughout this document. Unlike piles, **no new diagnostic code was written this round** — both generic diagnostics already exist and already name this scope in their own docstrings: `InspectElements.pushbutton` ("which categories/classes actually carry the tracked parameters, so the native adapter's collection sweep can be scoped correctly") and `InspectDimensionGeometry.pushbutton` (its own docstring already lists "piles/abutments/foundations" as the intended scope, and its core reference-resolution path — `GetGeometryObjectFromReference`, `Face.Project`, the nearby-element search — was never pile-specific; only the proximity-matching add-on at the very end is). Piles needed a third, purpose-built diagnostic (`InspectPileSetout.pushbutton`) only because the real question turned out to be schedule structure and bearing-text parsing, a kind of data neither generic tool touched — whether beams need an equivalent isn't known yet, and guessing at what it would need to answer before running the first two would repeat the exact mistake this project keeps naming.

**Real open questions this needs to answer, before any code:**

1. What element/category actually represents the bearing seat or soffit — Structural Framing, a custom family, or is "the beam" not a separate element at all?
2. Is there a parameter stating a design bearing-seat/soffit elevation directly, or does this have to come from geometry (`Location`, a specific `Face`'s Z)?
3. Is it drafted as a `SpotDimension` (elevation)? If so, does its reference resolve to real beam geometry via `Face.Project` the way deck/abutment dimensioning is already confirmed to generally work (§14) — or does it hit the same DetailLine/Detail-Component snap-workaround §17 just found on the plan-view coordinate spots, where the reference isn't what the value actually comes from?
4. Do real elevation values line up directly with Revit's internal Z (this project's existing mm convention), or is there a datum/level offset to account for — the same kind of question the Survey Point check (§14) had to settle for Easting/Northing.

**What to run:** open a real abutment section/elevation view, select a real bearing-seat/soffit element plus its spot elevation annotation, run `InspectElements.pushbutton` first, then `InspectDimensionGeometry.pushbutton` on the same selection. Treat the output like a capture (§2) — not committed. **Not yet run.**

**Run for real the same day — both diagnostics, one abutment (`03_SFR_ACS_Abutment_BR08_Retaining wall CS`, type `ABUTMENT SOUTH WEST_B08`, element `7926105`), two Spot Elevations (`Elevation_Survey 2.5`, elements `8190079`/`8190091`). All four questions answered cleanly, plus one real fact neither question anticipated:**

1. **Element/category**: `Structural Framing` — the whole abutment cross-section (ballast wall, headstock, keeper wall folded into one adaptive profile) is one instance per abutment end, not a separate discrete beam. Confirmed by the user directly: the family/category name is expected to vary client to client (matching the pile checks' own `RuleConfig.PileCategoryName` precedent — configurable, never hardcoded) — the setout-to-elevation-zero convention below is the real invariant, not this name.
2. **Design elevation parameter**: yes — `Start Level Offset`/`End Level Offset` (plain `Double`, decimal feet internally, this project's existing ×304.8 convention) give the real top-of-profile elevation at each end directly. No geometry derivation needed.
3. **Reference resolution**: both Spot Elevations' references resolve straight to the real beam element via `Face.Project` (`resolved_element_id` matches the selected Structural Framing instance exactly, for both) — **not** the DetailLine/Detail-Component snap-workaround §17 found on plan-view coordinate spots. Elevation spots on section/elevation views are a cleaner, different case from plan-view coordinate spots.
4. **Datum**: none needed — `Reference Level` is "Datum 0" at elevation 0, so the parameter is already an absolute real-world value. Confirmed by the user: "the setout to level 0" is the stable convention across projects, unlike Easting/Northing which needed the Survey Point transform (§14).

**The one real gap, not anticipated by the four questions:** the adapter's existing `dim.Value`/`ValueOverride` read — what every linear-dimension check uses — comes back **null for both Spot Elevations**, matching what the committed capture already showed generally (347/347 spot dimensions, `value_mm: null`, unconditionally, §17's investigation). The real elevation instead lives in `dim.Origin.Z`, which matches the parameter to the millimetre for both points sampled. So this check needs a new adapter read path (`Origin.Z`, not `Value`) — the same shape of fix `DimensionSegment.Origin` already was for linear dimensions once `GlobalPoint`/`Location` proved unreliable (§14's diagnostic-loop history).

**One loose end, not chased further:** both ends show a consistent ~0.835mm gap between the parameter and the spot's own value (20838.708mm vs 20837.873mm; 21179.870mm vs 21179.035mm) — small, real, and not investigated further since it's sub-tolerance either way; possibly the spot landing on a slightly different point on a sloped top surface than the profile's exact end vertex.

**Simpler shape than piles turned out to need** — no schedule, no proximity matching, no bearing/chain reconstruction, since the reference already resolves directly to the real element. **One real caveat before writing anything: this is one `FamilyInstance` (one abutment end), not several** — a second real sample from a different abutment is being gathered before any code gets written, same discipline as the pile checks needing several piles/dimensions confirmed before being trusted.

**Second real sample, same day — a different abutment family (`03_SFR_ACS_Abutment_CS`, type `ABUTMENT NORTHBOUND_BR8_2`/`_3`, two adjacent instances chained along a curved alignment) and three Spot Elevations. Both points 2 and 3 above turned out not to generalise:**

- **Reference resolution is mixed, not reliably direct.** Only one of the three spots (`5392639`) resolves to a real `Structural Framing` instance; the other two (`9324248`, `9332887`) both resolve to the same view-specific `FilledRegion` (a 2D fill/hatch annotation) — the same "reference isn't what the value actually comes from" problem §17 found on plan-view coordinate spots, just a different Revit class. Sample one's clean direct resolution was the easy case, not the typical one.
- **Even where it does resolve directly, the parameter match breaks down.** Spot `5392639`'s value (19389.916mm) is ~1.9-2.3m below its resolved element's `Start Level Offset`/`End Level Offset` (21641.955mm/21279.474mm) — not the sub-millimetre match sample one showed. **Confirmed by the user: this is real, not a bug.** `Start`/`End Level Offset` is the profile's crest; the three spots in this sample measure the bearing shelf a girder actually sits on, genuinely below the crest. Sample one's near-perfect match was a coincidence — that `FamilyInstance` was "an extension of the abutment that is like a retaining-wall capping beam," where the crest *is* the critical setout value; this sample's instances are the actual bearing portion, where the shelf is. Which real part of the abutment a given `Structural Framing` instance represents genuinely varies, and there is no reliable parameter name for "the shelf" specifically (this family doesn't even expose the sub-component height parameters — `Abutment_HeadstockShelfHeight` etc. — sample one's family had).

**Consequence: a check here can't trust a named parameter or the spot's own Reference — it needs real geometry, the same escalation this project's diagnostic history already made once for linear dimensions when `GlobalPoint`/`Location` proved unreliable (§14).** `InspectDimensionGeometry.pushbutton` extended the same day: `_collect_structural_framing`/`_nearest_structural_framing` (2D nearest-neighbour by `OST_StructuralFraming` Location, same technique `_collect_piles`/`_nearest_pile` already use) plus new `_horizontal_faces`, which walks an element's real solid geometry (`Element.Geometry` → `Solid.Faces`/`GeometryInstance.GetInstanceGeometry` for nested `FamilyInstance` geometry) and lists every roughly-horizontal `PlanarFace`'s real Z, sorted by 2D proximity to the spot's own Origin — geometry can't lie about where a horizontal surface is, regardless of what the Reference or a parameter claims. Every new Revit API member verified against the real `RevitAPI.dll` before writing this, same discipline as everywhere else in `native/`.

**Run for real the same day (after a real deployment mix-up — the update sat unpushed to GitHub for several rounds before actually reaching the branch, not a Revit-side problem) — two real bugs found in the probe itself, both fixed before the next run:**

1. **Only 2 horizontal faces came back for a real abutment cross-section that should have several real steps** (crest, shelf, base). `Options()`'s default `DetailLevel` (`Coarse` when unset) collapses a parametric civil profile to a simplified bounding block, not the real detailed geometry a Fine-detail drafted section actually shows. Fixed: explicit `options.DetailLevel = ViewDetailLevel.Fine`.
2. **The single "nearest" pick was too fragile.** A curved/chained abutment is several adjacent `Structural Framing` instances (§18's second sample already showed two chained together), and a `Location` point is a curve midpoint that can sit several metres from where a given spot elevation actually is — real distances seen on this run: 1.9–8m, close enough to plausibly pick the wrong instance outright. `_nearest_structural_framing` (singular) became `_nearest_structural_framings` (`STRUCTURAL_FRAMING_CANDIDATE_COUNT = 3`), walking the several nearest candidates and merging their faces into one list sorted by 2D distance, rather than betting everything on one guess.

Neither fix was confirmed sufficient in isolation — the first run's data (too few faces found, at distances too far from any spot value to trust) couldn't tell "wrong detail level" and "wrong candidate element" apart, so both were fixed together before asking for another run.

**Re-run confirmed the `DetailLevel` fix (99/64/55 horizontal faces now, up from 2/11/9) but the Structural Framing search still isn't converging on a confident match.** The closest-by-Z candidates (10mm/35mm/109mm off) all sit 2-7m away in plan — too far to trust as the same physical shelf without independent evidence of a real crossfall that size. **A different, independent signal pointed at a better lead instead of iterating the face-walk further:** the existing, category-unfiltered `nearby_geometry` search (750mm radius, already built for the linear-dimension work) found two `Generic Models` `FamilyInstance`s (elements `5458522`/`5458562`) sitting within 750mm of two of the three spots — much closer than any Structural Framing candidate. Likely the real bearing pad/plinth as its own separate family, not part of the abutment's own solid. **Next: select those elements and run `InspectElements.pushbutton` on them** — if confirmed, a bearing pad/plinth's own `Location.Point.Z` or a parameter would give the shelf level directly, more precisely than searching the much larger retaining-wall-profile solid.

**Ruled out by the user directly: those two `Generic Models` instances are part of the retaining wall itself, not a separate bearing pad/plinth.** No new element lead — back to the Structural Framing search, this time by fixing the reading logic itself rather than guessing at a fourth external cause. **Third real bug**: `z_mm` was read at `PlanarFace.Origin` — an arbitrary point on the face's own untrimmed plane, correct only for a perfectly flat plane. A real shelf with any longitudinal grade/crossfall (common, for drainage) has a genuinely different Z at `Origin` than at the spot's own location, on the *same, correct* face — plausibly explaining the 10-500mm residuals at 2-7m distances from the previous run. Fixed by reusing `Face.Project(near_xyz)` — the exact technique this diagnostic already proved for linear dimensions — to read Z at the real projected point nearest the spot, not an arbitrary one.

**Confirmed on a real re-run, same day — 2 of 3 spots matched exactly.** A fresh selection (three different Spot Elevations, elements `6825741`/`6825752`/`9324286`): `6825741` and `6825752` both landed `delta=0.000mm`, `distance_2d_mm=0.0`, `z_read_at_projected_point=True` — `Face.Project` found the real shelf face and its Z matched the spot's own stated value exactly, the same precision the pile checks needed before being trusted (31/32 sub-millimetre, PLANNING.md §14). The third, `9324286`, came back 22mm off at 1.2m, `projected=False` for every one of its 3 candidates — none of the 3 nearest Structural Framing instances by Location-point distance actually contained the real shelf face under it; a wider candidate net (not limited to 3, which the diagnostic used to keep its own JSON small) is the likely fix, not a deeper problem with the technique. **This is real, strong enough validation to move to designing the actual Core check** — see the next entry.

**Corrected before designing that check, per the user directly: category-filtering was never going to hold up, not just too narrow at 3 candidates.** "We cannot limit this to structural framing, it will fall over as soon as we put another model into it, these could be generic models, 2 point adaptive families, abutments etc. Using structural framing for these elements is an old workflow and something we will be phasing out." Structural Framing isn't even a stable category *within this one client's own project history*, let alone across clients — a sharper instance of CLAUDE.md's own "logic built on a client convention breaks" lesson. Fixed the same day, before any real-check design work: `_collect_structural_framing`/`_nearest_structural_framings` (category-filtered) replaced by `_collect_geometry_candidates` (category-agnostic) — a small 3D bounding-box search around each spot's own point (`SHELF_SEARCH_RADIUS_MM = 1500.0`, generous but not calibrated), minus the same noise-category/class exclusion `_nearby_elements` already uses, not a category collector at all. Real data already justified a small radius (the two exact matches above both had `distance_2d_mm=0.0` — the spot's own point can sit exactly on the real shelf face). **This changes the real check's own design too — it must not filter its geometry search by category either. Needs one more real run to confirm the category-agnostic search still finds the same real matches before any Core check gets built.**

**Confirmed on a real re-run, same day — all 3 spots now match, not 2 of 3.** The two previously-exact matches (`6825741`, `6825752`) stayed exact (`delta=0.000mm`, `distance_2d_mm=0.0`). The third (`9324286`), previously 22mm off at 1.2m under the category-filtered search, is now **2.3mm off at 0.04mm** (`z_read_at_projected_point=True`) — the category-agnostic search found the real element (`5355699`) that the Structural Framing-only search had simply never considered. 2.3mm is well within normal measurement/rounding noise for this project (`MeasurementEpsilonMm=0.5mm`, `RoundingGridDefaultMm/2=2.5mm` are the closest existing precedents). **This is complete, clean validation across all 3 real spots sampled — ready to design and build the real Core check.**
